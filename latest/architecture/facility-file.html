Facility File and Its Views#

OSPREY keeps one description of a facility and derives everything else from it. The sources under data/facility/ are combined by osprey build into the facility file, and each service reads a view of that file, a file in the shape the service needs. No service keeps a channel list of its own, so the channel finder, the limits check, the simulator and the knowledge graph cannot disagree about which channels exist or what they are.

Writing the sources is in Describe your facility. This page is about what the build makes of them.

The facility file#

build/facility.json is every record of the facility in one document, under a schema header: identity, classes, places, devices, channels, groups, models with their wiring, limits and scenarios. It holds two things no source file does. The first is what the build computes: the readback a setpoint is paired with when no source names one; each device’s place and position along its model’s deck, its ordinal among its class in its place and in its model, and the groups that name it; and each wiring record’s direction, unit, value range and start value. The second is provenance: per record, which layer and file stated each field, which fixes were applied and which fields the build filled. osprey facility show <id> prints it.

The file is the same in every render of a build. It carries no timestamp, no OSPREY version and no absolute path, so equal sources give equal bytes.

Two halves of the build#

The first half makes the facility file, once, in memory. It runs in fixed stages and a stage runs only when every earlier one is clean:

Stage

What it does

load

Parses each source file and refuses unknown keys and fields only the build may write.

combine

Merges the layers field by field, stops on two layers that disagree, applies fixes.yaml and fills the defaults.

schema

Holds the combined file to the facility-agnostic schema.

references

Every id a record names exists; device classes and signal roles are known.

records

The pair, value, limits and seed rules.

wiring

Fills each wiring record’s direction, unit, value range and start value from its model’s engine.

compute

Positions, places, ordinals and groups, read off the decks, and the checks only a deck can answer.

measurement

Holds each measurement file to the kinds it allows, against the groups and instruments its model wires.

knowledge

Names each knowledge page linked to a device the facility lacks. Warns and never stops.

The second half writes. A build renders more than one tree (the deployment’s own, one per persona, one per container image) and each render receives the same facility file and the views its configuration and served models call for. A view a render does not carry is named once on stderr, with the configuration key or the model fact that left it out; a channel-finder index the profile did not select is neither written nor named.

osprey facility validate runs the first half and the main profile’s render into a temporary directory, adds the response check of a Middle Layer import, and writes nothing into the repo. Persona and image renders are checked by osprey build alone.

The measurement tools, and the approval prompt, which shows the view’s digest the facts record carries.

pyAML. One configuration per measured model: its arrays, magnets, BPMs, RF plant and tools, read from the facility file and the model’s measurement file, beside the deck its design simulator runs on; a model solved single_pass has none. Each group role is one array, named after its group, or after the role when the role names several groups. A periodic model whose measurement file allows trm or crm and names the instruments they read (tune, and rf for crm) gets trm.json or crm.json, the design response of its quad or sext group, whenever every member has a finite modelled column; the tune or chromaticity correction tool that loads it is added only when the matrix has rank two. The build names on stderr each served model it gives no view (it names no deck, or has no measurement file) and each setpoint it leaves out, with the reason: pyAML has no magnet model for it, or its slices mix zero-length and thick elements.

Simulator. The view lists every channel address of the facility and each served model’s status address (addresses.json), every model with its wiring (variables.json), the models this render serves (served_models.json), the seeds, the scenarios and a byte copy of each deck. A simulator serves exactly the channels of addresses.json; an address outside it does not exist.

Limits. One entry per record of limits.yaml and nothing else. A channel without a record is decided at write time by control_system.limits_checking.mode.

Facts. What agents are told about the facility: its identity, the place tree with device counts, the device classes with their aliases, the signals in use and the models. It is how an agent knows the facility’s own words without a prompt written by hand.

Bluesky. One settable per setpoint and one readable per readback. A settable reads back its pair when the pair is another channel, and settles within the setpoint’s tolerance, else within the motion its readback’s seed declares, else within the profile’s floor.

Channel finder. Three indexes, one per file-backed pipeline; a render carries the one its profile’s channel_finder_mode selects. The fourth pipeline, graph, reads data/channel_databases/graph.duckdb, which the build indexes from the Turtle that services.graphdb.ttl_path names: the graph view, unless the profile names another.

Graph. The facility file as Turtle: one node per place, device and channel and per signal named, with the device classes as a class tree.

The schema#

The facility file’s shape is two LinkML modules in src/osprey/facility/schema/: core.yaml, the records, and vocabulary.yaml, the device classes, signal roles and property names. Both carry NARAD’s schemas forward. NARAD requires more than a bare channel list can state, so loosenings.yaml records, per slot NARAD requires, what became of it (dropped, optional, renamed:<slot> or header) and why. The graph view writes the facility file back in NARAD’s terms.

A facility adds device classes in classes.yaml, each under a vocabulary class or one it added earlier; they reach the facts view and the graph with their aliases. Signal roles are closed: a channel’s signal is one the vocabulary lists. The build pairs setpoints with readbacks by the quantity their signals name, so a quantity the vocabulary lacks pairs only through an explicit pair.

Simulation models#

A facility file’s models are what stands behind the channels when the deployment runs against a simulator. Each model record names an engine, a deck and the wiring that ties channel addresses to elements of the deck.

Engines are plug-ins. An engine is a module registered in the osprey.simulation.engines entry-point group under the name a model’s engine gives. OSPREY ships pyat. The build reaches the engine to read the deck (where each element sits, each wired channel’s operating point, what each wiring record is) without building a model, and stops with engine-missing when no installed package registers the name. The contract is under LUME model.

The texture model serves the rest. Every channel no served model wires is served by texture, from its seed: a setpoint holds the value written to it and echoes it into its paired readback, and every channel moves with the noise and drift its seed states. texture is always served, so a facility with a channel list and no physics model is still a whole machine to a client.

A render chooses what it serves. simulation.models names the physics models a render serves; absent, it serves every model the facility file holds, and [] serves texture alone. The choice is written into the simulator view’s served_models.json. Every model’s record and deck are in the view whether or not it is served, so the set can change without a different view shape.

A failed model does not take the machine down. Each served physics model has a status channel, <code>:SIM:<model>:STATUS, which exists in no other view. A model whose engine raises while building or reading it (over a deck that does not load, say) is left failed: its status channel carries the engine’s error text, and every other model and every texture channel is still served. osprey sim status prints one <model>: <status> line per served model, ok or that text, and names each model’s log.

How the composite serves the models over Channel Access and PVAccess is in Virtual Accelerator.
