Build Your Own OSPREY Apps#

An app is your deployment’s own tool for one task on the machine — trim a corrector, show and set a channel, step a magnet through a table — used by the operator from a page in the web terminal and by the agent from its tools. It is how a facility extends OSPREY with its own workflows without changing OSPREY itself: the app lives in your deployment repository, is built and started with the rest of the deployment, and writes to the machine only through the same chain as every other write.

An app is made of up to five parts, all described by one file, apps/<name>/app.yml. None is required by itself; an app has at least one and carries only the parts its task needs:

  • a backend container — a small web service, in Python, that holds the app’s code and state, reads the machine and writes it;

  • a panel — the page the operator opens from the sidebar, served by the backend and shown inside the web terminal;

  • a tool server — an MCP server that gives the agent tools for the same task;

  • skills — instructions that tell the agent when and how to use the app;

  • subagents — agents of the app’s own that the main agent hands a task to, each with the tools it needs.

A panel always needs a backend, which serves the page and holds what it shows. A tool server needs one for a tool that writes to the machine and for any state the tools keep; without one it only reads or computes, keeps nothing between calls and opens no data store of the deployment. Skills and subagents need no backend. So an app can be a skill and a subagent with no code of its own, a set of read-only tools, a backend with a panel, or all five. With a panel and a tool server over one backend, what the agent computes is what the operator sees in the panel, and what the operator sets in the panel is what the agent reads back.

osprey build turns app.yml into the parts it lists; osprey up starts them with the rest of the deployment. osprey app new copies a minimal working app — one channel, shown in a panel, read and set by two tools — as the starting point for your own. This section uses it as its example, under the name corrector-trim.

Prerequisites: a deployment repository (osprey init) and the terms from Privilege Tiers: a login opens a terminal with a tier, and the operator’s write switch per machine decides whether a write is refused, asked or allowed.

What the operator sees#

In the web terminal’s sidebar, under Apps, the app is a row with the label its manifest gives it. Clicking it opens the panel as a tile beside the chat; the panel takes the terminal’s theme, light or dark, because it uses the terminal’s design tokens. The row dims while the backend does not answer its health check and lights up again when it does (Panels).

The panel talks to the backend for that operator: the terminal passes the login’s name along, so the backend answers from the machine that login’s session is on — the one named on the control-target chip — and shows that login’s plan, not another’s.

A write started from the panel (a button such as Apply…) opens the panel’s own confirmation with the exact setpoints. A write the agent starts shows in the chat as an approval card when the operator’s switch for that machine is at asked: the card names the app, the tool, the machine (Live — writes move hardware, Simulator — nothing moves), the switch position, and then the text the app wrote for it, filled in from the backend’s state — the channel, the new value and the current readback, or one line per channel for a write of several setpoints. The operator approves or refuses. At allowed the same write runs without a card; at off it is refused.

On a login whose tier is never, and on every shared login, the panel is read-only: it shows state, and the terminal refuses the panel’s write requests before they reach the backend.

What the agent sees#

The app’s tools, named mcp__<app>__<tool> — mcp__corrector-trim__read_channel and mcp__corrector-trim__set_channel for the example — beside OSPREY’s own tools. Each tool’s docstring is what the agent reads to decide when to call it, and the manifest says which tools only read and which write:

  • a read tool runs like any other tool;

  • a write tool is listed under approval in app.yml, so every call meets the tier, the write switch and the approval before the tool runs.

An app can carry a skill: a SKILL.md that tells the agent when to use the app and how to read its answers. The example’s skill says to read first, tell the operator the current value, and only then call the write tool.

An app can carry a subagent: an agent of its own, with its own instructions and tool list, that the main agent hands a task to. The main agent’s brief gets one note per subagent saying when to delegate, and the work runs in the subagent’s context instead of filling the main one — the right shape for a task that reads a lot to answer a little, such as a search.

The build installs skills and subagents into every login that shows the app.

Where the app has a backend, the agent’s tools reach it only at the routes the manifest declares, through the web terminal, under the login’s name — never directly, never as another login. When the backend does not answer or refuses a call, the agent sees the sentence you wrote for that case in app.yml (errors.unreachable, errors.refused).

When to build an app#

The full shape — backend, panel and tools — is right when a task needs its own state and its own view, for the operator and the agent alike, the same in every session. Other shapes cover the rest:

You want

Build

A one-off calculation, plot or check

Nothing. Ask the agent; it writes and runs Python under the same tier and switch (Python Executor).

To tell the agent how to do a task with the tools it already has

A skill — instructions, no code of your own runs (Agent Skills). Put it in an app with no other part when it should be switched per login like an app.

A measurement sequence with a queue, a run record and live plots

A Bluesky plan (Bluesky Plans).

An existing web page of your facility in the sidebar

A URL-backed panel (Panels) — nothing to write.

A task with state (a plan, a table, a model), a page to work it from, and tools so the agent can do it too

An app — this section.

A task that ends in several coordinated writes shows the difference. It is not one write: it is a plan — the inputs, the setpoints computed from them, the predicted effect, a limit verdict per setpoint — that the operator inspects and the agent reasons about before anything moves. The plan has to be the same object for both, has to survive a page reload, and has to be the thing the approval card binds the write to. That is an app.

What you write#

One directory in your deployment repository. osprey app new <name> writes all of it from the scaffold, with your name in place:

apps/corrector-trim/
  app.yml                 the manifest: name and the parts the app has
  pyproject.toml          the Python package the backend and tools are in
  corrector_trim/
    __init__.py           the app's name and the routes the two sides share
    server.py             the backend: a FastAPI service, serves the panel,
                          answers state, performs the write
    tools.py              the tool server: one function per tool
  panel/
    index.html            the page, using the terminal's design tokens
    panel.js              reads the backend's state and shows it
    panel.css
  skills/
    corrector-trim/
      SKILL.md            the skill: when and how the agent uses the app
  tests/
    panel.test.js         Vitest over the panel

The scaffold is the full shape with one skill. Delete the parts your app does not need, with their blocks in app.yml; add a subagent as one file, agents/<name>.md. Everything in it is ordinary FastAPI, JavaScript, YAML and Markdown. What OSPREY supplies, so the app does not have to:

  • the connection to the machine — the backend asks for a connector and reads or writes channels through it; the connector applies the write verdict, the limits and the audit record;

  • who is asking — the terminal passes the login’s name to the backend, and the SDK turns it into that login’s control target;

  • the panel’s place — the sidebar row, the tile, the theme, the health dimming, and the proxy that keeps the panel reachable only through the terminal;

  • the tool server’s wiring — serve_tools runs your functions as an MCP server with the right name, and the approval card, the stamp and the re-check on the tool side come from the manifest’s approval entry;

  • the build — the wheel, the image, the container, the port, the config file, the state directory, the installation of skills and subagents per login.

App code imports OSPREY only through osprey.apps.sdk (plus osprey.facility.kinds and the public osprey_connectors modules). Every name in the SDK keeps its meaning across releases; osprey app check reports any other import, so an app built today still builds on the next OSPREY.

How writes stay safe#

An app adds no new way to write to the machine. Whether the write starts in the panel or in a tool:

  1. The tier of the login decides whether the app may write at all (control_system.writes: never | asked | allowed). On never, and on a shared login, the terminal refuses the panel’s write requests and the agent’s write tools are denied.

  2. The write switch the operator set for the session’s machine decides each write: off refuses, asked shows the approval card, allowed runs without one.

  3. The approval binds the write to what was approved: the app’s manifest says what the card shows and which values of the backend’s state the call is held to. The example binds the readback the operator saw; an app that applies a computed plan binds the plan’s id and a digest of its setpoints, so a plan that changed after approval is refused.

  4. The connector judges the write once more — verdict, limits, read-back — and records it, as it does for every write in OSPREY (Safety Chain).

Writes and approvals on the build page says how to declare a write tool and what each key does.
