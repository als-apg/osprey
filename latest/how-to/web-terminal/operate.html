Run the Web Terminal#

Start the Web Terminal from any OSPREY project directory:

osprey web

It boots a local server on http://127.0.0.1:10100 and prints a login URL of the form http://127.0.0.1:10100/?token=…. Opening that URL (your browser opens it for you) signs you in and then redirects to the clean http://127.0.0.1:10100 address; every later request rides the cookie it sets. That cookie is good for 12 hours by default and outlives closing the browser, so on a console other people sit at, shorten it — set modules.web_terminals.auth.session_lifetime in the deployment’s config (see Require a Login). The URL is printed once, but the token in it is the server’s own secret and keeps working for as long as that server runs — treat it like a password rather than a one-shot code.

If OSPREY_TERMINAL_SECRET is already set in the environment you launch from, osprey web uses that value rather than minting one, and says so instead of printing a URL — the URL was printed wherever that secret came from. Unset it and start again to get a freshly minted one.

Override the defaults, or point it at another project, with --host, --port, and --repo.

To keep it running after you close the terminal, start it in the background:

osprey web --detach     # start in the background
osprey web stop         # stop it again

In background mode the process id and logs are written to var/osprey-web.pid and var/osprey-web.log in the project directory. The login token lives only in the running process’s memory and is never written to disk, so if you lose the printed URL there is no way to recover it: stop the server and start it again (osprey web stop then osprey web --detach) to mint a fresh one. Browsers already signed in stay signed in across that restart — their sessions live in a store on disk; osprey web sessions clear (with the server stopped) forgets them.

What you get#

The window has a sidebar on the left and two panes:

  • Sidebar (left) — the list of everything you can open, in both views: the control-target block (which machine this deployment writes to, and whether it may), search, the Workspace and Tools sections, and a footer with Docs, Feedback (see Send and Retrieve Feedback), Sign out (multi-user deployments only) and ☰ More. See The sidebar.

  • Agent (right) — a real terminal running the OSPREY agent in Expert view, or the operator chat in Simple view. It survives reconnects, and you can keep a few background conversations alive and hop between them. Close the pane with its ×; the Agent row in the sidebar opens it again.

  • Work pane (middle) — the artifacts and panels you open from the sidebar, arranged as dockable tiles. New artifacts, plots, and data files appear in the sidebar’s Artifacts list as the agent creates them, with no refresh. On a fresh deployment the list is not empty: the control-assistant preset ships one interactive example plot (synthetic data). It is there for you, not the agent, which never lists or cites it. Delete it when you no longer want it; it does not come back. It is switched on by artifact_server.example_artifact in config.yml. Your control-system tools (Channel Finder, ARIEL, the lattice dashboard, and so on) open here too. See Panels.

The settings drawer (☰ More › Settings) lets you read and edit the project’s config.yml — and the agent’s own setup and memory files — from the browser, so you rarely need to drop back to an editor. Changes prompt you to restart the terminal so the agent picks them up.

Copying text works the way it does in a desktop terminal: drag over the agent’s output and the selection is already on your clipboard — no key to press. To grab raw screen text instead (say, while the agent is busy), hold Option (macOS) or Shift while dragging, then copy with Cmd+C or Ctrl+Shift+C; plain Ctrl+C always interrupts the agent. Serve the terminal over HTTPS for this to work in every browser — on a plain http:// page copying falls back to an older browser mechanism that Safari may refuse.

One session, both views#

Expert and Simple are two windows onto the same conversation. Pick the other one from ☰ More in the sidebar and the agent you were talking to comes with you: the terminal and the chat share one session, one write state and one transcript, and only the view you are looking at runs the agent.

A deployment can offer the Simple view alone. With web.expert_view: false ☰ More has no View group and every terminal opens in Simple; see Expert and Simple view.

Handing it over waits for the work in flight. Switch while the agent is mid-turn and the view you arrive in reads Finishing in the other view with the time you have been waiting, and offers Stop and switch now. Let it finish and the conversation reappears where it left off, with everything said so far already in the log. Nothing is ended on a clock: only the turn finishing, closing the page, or that button ends it. The button interrupts the agent, and stops it outright if it has not yielded within five seconds.

Flip views while the other side’s agent is idle and there is nothing to wait for: the view you arrive in reads Restarting the agent in this view…, with no clock and no stop button. A restart that runs past about four seconds turns into the wait above.

A refusal can meet you instead of the wait. This session is in use in another tab or view. means another browser tab holds it, so close that tab or work there instead. The previous agent is still shutting down. is the one worth retrying, and the card offers Retry.

Note

Deployments built before this release. The wait needs the turn-state hook, which tells the web terminal when a turn starts and ends, and a deployment scaffolded earlier does not have it: add turn-state to the profile’s hooks: list and run osprey build. Without it, switching away from a terminal that might be working never waits. It says The other view may still be working. and offers only Stop and switch now, and a terminal that was idle all along can still take the full five seconds to hand over.

The two views run the same Claude Code version, the one claude_code.cli_version names. If the chat is refused because that version is not installed, the server log says which one to install; see Installation.

While a turn runs in the Simple view, the composer is disabled and Send becomes Stop. Send the next prompt when the agent finishes, or select Stop to end the turn.

Clearing a conversation#

Run /clear in the terminal to start a new conversation under the same session. The write state and the machine you are standing on carry over, and the chat shows the cleared conversation too.

Beneath the composer, a context meter shows how full the context window is. From 80 percent it suggests /compact or a new conversation.

Attaching a file#

Attach a file to a message with the paperclip button. You can also paste an image, or drop a file on the composer. The file is uploaded when you attach it. The chip shows the file name and its size. To remove a chip, select its x button. Type your question, then send. The chat does not send a file by itself. The agent opens the file with its Read tool.

The chat accepts images (PNG, JPEG, GIF, WebP), PDF files, and plain-text files (TXT, LOG, CSV, JSON, YAML, Markdown, Python). A file can be 20 MB at most. A message can carry 10 files. One chat can hold 200 MB of files. A file of another type, or a file that is too large, is refused. The chip shows the reason.

The agent reads an attached file from the uploads directory under the agent data directory. The deployment allows the agent to read that directory, so the read raises no approval card. A file outside it can still raise one. A file that you attach but never send is deleted after 24 hours.

The control-target chip#

The sidebar carries a block that answers, at a glance, the question every write depends on: if the agent writes now, which machine does it land on, and may it? It is one row: an icon with the machine’s dot, the machine’s name, the write state, a dot for the health of the deployment’s services, and an arrow. It reads like this:

⌖ Rehearsal  writes asked  •  ⇕

Put the pointer on the block to see the same facts as one sentence, for example Control system: Rehearsal, writes asked. Put the pointer on the small health dot to see the health of the services.

The first part names the machine this deployment stands on, by what it is:

  • Live — the facility’s own. Writes move hardware.

  • Rehearsal — a copy of the real machine’s controls, same channel names, no hardware behind it. Nothing moves.

  • Simulator — the virtual accelerator: a physics model with beam in it, served from its container or in process. Nothing moves.

A deployment can put its own names on its machines (Example Research Facility storage ring rather than Live); what the machine is stays behind the small ⓘ beside its name either way, and that tooltip also keeps the controls server’s own technical label.

The second part is your login’s write switch for that machine, and what the next write would get:

  • writes asked — every machine write asks you first, in the approval card.

  • writes allowed — the same writes run without a prompt.

  • writes off — writes are refused. Reads are untouched: the agent keeps its full view of the control system and of the project, and can still run analysis, plots and read-only Python.

  • writes locked — your switch is armed, but something the chip cannot lift refuses the write. The popover shows the phrase for it and who lifts it.

A switch is one login’s. Two logins on the same machine each have their own, and one login’s position never changes the other’s writes.

Click the chip and a popover opens next to the sidebar on every control target the deployment configures, not only the one you are standing on. A click outside the popover, Escape, or a change of the window or sidebar width closes it. When a confirm dialog is open over the popover, the first Escape closes only the dialog.

The machine you are on, and the others#

The machine the agent stands on is a card at the top: its name and its writes switch. Every other machine is a row below the card with the same shape and the actions. What writing to a machine means (Writes move hardware, or one of the nothing moves lines) sits with its endpoint and the server’s own label behind the small ⓘ beside each name, on hover or keyboard focus:

  • The writes switch — per machine, for every session of this login: off, asked or allowed. Off is always available. A position your tier or a lock forbids is disabled, with the reason on hover.

  • Switch to — moves the deployment onto that machine. Where a switch is not available, the button’s place is taken by a short phrase for the reason — not set up, needs gateway ack — with the server’s full sentence on the tooltip. On a fresh deployment the real machine reading not set up is the normal state, not a fault: authoring its gateways is the go-live edit.

A machine that stops answering says so — not answering, in red, next to its name. A machine that answers says nothing about it. Endpoints, gateway roles and the age of the last probe stay on the tooltips and in the confirmation dialogs, where the decision is actually made.

The foot has Turn all writes off: every switch of your login goes off in one click, a machine no longer configured included. It stops your login’s writes only; other logins keep theirs. It is enabled while any of your switches is armed.

Turn writes off, or on#

The switch is per machine. Turn the real machine off and work on the simulator carries on, which is the point: you put the machine you are worried about out of reach without giving up the one you are working on.

Narrowing (to asked, or to off) applies as you click, and nothing refuses it — no lock, no read-only run, no second terminal. If a stop cannot be recorded you are told plainly that it did not take effect; the chip never shows an off that was not recorded.

Widening asks first. The confirmation names the machine and says whether writes will still prompt. Tick Don’t ask again on any machine to skip it for every move to asked or allowed, the live machine included; Shift-click or Ask again in the popover brings it back. If a stop lands while you are confirming, the move does not take effect: the chip re-reads and you click again.

Nothing is restarted. Every gate reads the switch at the moment of the write. A narrowing reaches every next write, runs already going included: the agent’s next tool call, a running notebook cell’s or Python run’s next write. A widening reaches the agent’s tool writes at their next call; a notebook cell or Python run already going keeps the position it started with, and the next one follows (Notebooks). The confirmation says so.

What the chip cannot lift. A write is refused for one reason, the first that holds, and locks no click lifts come before the switch. The chip shows that reason’s phrase on the row, and the agent is refused in the same words. Each phrase ends by naming the machine — (Concerns the rehearsal machine.):

Phrase

Who lifts it

the deployment is running read-only

The deployment admin. The chip cannot.

this login’s write tier does not allow them, this login’s write tier is not known

The deployment admin.

this scheduled or triggered job runs for no login

The deployment admin. No switch covers it.

this machine’s writes belong to another login

Only that login.

the machine this connector writes to is not known, the write switch cannot be read, the write gateway has not yet followed the switch

Retry, then the deployment admin.

this run was started with writes held off

Run it again without the pin.

Writes are off, a stop came after the turn-on began

You: move the switch to asked or allowed.

A position past your login’s tier (Privilege Tiers) acts as the tier until the tier is restored.

Switch the deployment to another machine#

Switch to on a row moves the whole deployment onto that machine, after a confirmation that says where every control read and write goes next and your switch’s position there — the switch is per machine, and it does not travel with you. This dialog too can be skipped with its own Don’t ask again on any machine. The page that holds the control context runs the same checks the agent’s own switch runs — that the move is allowed, and that nothing is mid-flight on the machine you are leaving — and records the outcome; the deployment’s control-system servers then move themselves onto it and report when they have arrived. The row reads switching… until every one of them has, and then ✓ switched, or ✗ with the phrase for the refusal — the same refusal, for the same reason, the agent is given. A server that could not make the move says so by name, so you know which one to look at. If nothing answers within 30 seconds the row reads request_expired: nothing that could carry out the switch was alive to pick it up. The outcome line leaves the row after about a minute — an outcome is news for as long as someone is watching for it.

Ask for a second switch while one is still landing and it is refused rather than queued, naming the servers still working. Wait for the chip to settle and ask again.

Switch to is the one control a second web terminal of the same login does not hold: only the process holding the control context moves the deployment, and elsewhere the button’s place names the holder. The writes switches work from either.

What the switch itself is gated on — the approval prompt, the limits posture, the archive — is Switch the Control Target at Run Time.

Where the control target and the write state live#

Both belong to the login the terminal acts as, not to any one session, and nothing is written to config.yml. Every session, window and notebook kernel of that login sees the same machine and the same switches: turning writes off on a machine takes them away from all of them, and a switch made in one window applies in the other. That is the point — a switch you can only see from the page you happen to be on is not a safety control.

Both are recorded together on disk, written as soon as you click and read back when a server starts, so restarting the container never quietly widens a switch or moves the deployment off the machine somebody put it on. Coming back to the deployment baseline is a switch like any other.

That record sits in a directory named for whoever the terminal is acting as: var/agent_data/control_target/<name>/control_context.json. On a multi-user deployment every user has their own container and their own volumes (Multi-User Support), so “the deployment” here means the stack that user is working in, and <name> is that user — alice’s settings are in control_target/alice/ on the host, and no user’s chip decides another user’s writes.

What refuses a write, and how firmly#

Each write route is refused by the layer that owns it. One of them is best-effort rather than enforced:

What the agent tries

What refuses it

What that means

channel_write — any control-system write

The connector, before the control system is asked

Enforced. The writes-check hook denies it first as well, but the connector is the layer that holds if the hook does not run.

execute with execution_mode="readwrite"

The Python executor’s own gate

Enforced. The run is refused outright; a readonly execute is unaffected and runs normally.

Any other write tool the writes-check hook covers — for example the Bluesky queue’s arming tools, where that server is enabled

The writes-check hook

Best-effort. It is the first hook in the chain and the only switch-aware layer those tools have; a hook that fails to run does not refuse.

Every layer speaks the phrase from the table above, so a refusal never sends you to the wrong control. A switch you turned off sounds like “Writes are off; turn it on from the chip in the web terminal. (Concerns the real machine.)” — and the chip is where you move it. A read-only run says the chip cannot lift it, and a refusal nobody set — a switch that cannot be read — says to retry, then ask the deployment admin.

Note

The other surfaces. Simple mode’s chat and the operator websocket run their agent through the Agent SDK rather than a terminal, and notebook kernels run no agent at all. All of them read your login’s switches at write time, so a switch you set and a move you make reach every one of them — and the full chip works in both views, because what it changes is your login’s record rather than anything belonging to the window you are looking at.

A notebook kernel is the one surface where when is worth knowing. Off refuses the running cell’s next write; a widening, or a move to another machine, reaches the next cell you run. See Notebooks.

Where a deployment also serves a panel at an address of its own, that address is a service door, not a terminal. Log in there directly and the deployment has no name to put on what you do, so no switch covers it: a plan queued from that page writes nothing (owner_unknown). Reaching the same panel from its tab in the terminal is the named path, and the one the chip governs.

The sidebar#

The sidebar is on the left in both views. From top to bottom, it shows:

  • The OSPREY mark and the label toggle.

  • The control-target block. It is one row that shows the machine that this deployment writes to, if the agent can write to it, and the health of the services. Click the block to open the control-target popover.

  • Search. It opens the command palette. The shortcut is ⌘K on macOS and Ctrl+K on other systems.

  • The groups of panel rows. At first there are two, Workspace and Tools:

    • Workspace starts with these rows:

      • Agent opens the agent pane, or moves the focus to it. When the pane is closed, the row shows a hollow dot. When the agent waits for your answer, the row shows the number of open questions. Agent is always the first row of the first group.

      • Artifacts opens the work pane and lists the artifacts of the agent. Click a row to show that artifact in the work pane.

      • Script runs lists the run records. It is always below Artifacts.

      • Events shows only when the deployment enables the events panel.

    • Tools starts with all other panels that this deployment enables.

    In each group, the rows are in your order. + Add panel is always the last row of the last group. See Panels.

  • The footer: Docs, Feedback, Sign out and ☰ More. Sign out shows only on a multi-user deployment. See Sign out.

When the window is short, only the group that holds Artifacts and Script runs scrolls. The other groups and the footer always stay on the screen.

Arrange the groups#

You can rename the groups, add your own groups, and move rows between them.

To change a group, put the pointer on its name and click ⋯. The menu has these items:

  • Rename. Type the new name and press Enter. Press Escape to keep the old name. A name can have up to 40 characters. An empty name keeps the old one.

  • New group below. This adds an empty group below this group and opens its name for editing.

  • Move up and Move down. These move the group in the sidebar.

  • Delete group. This item shows only for a group that you added. The rows of the group go back to Tools. You cannot delete Workspace or Tools, but you can rename them.

To move a row to a different group, do one of these:

  • Right-click the row and pick Move to and the name of the group. Pick Move to new group… to put the row in a new group below its current group. Then type the name of the new group.

  • Drag the row into the other group. Release it where it must go.

You can move each row except Agent. Script runs moves with Artifacts. A group without rows shows “No panels — move one here from a row’s menu”.

Your groups are kept in this browser, for your user only. They do not change the sidebar of other users.

Hide the labels#

To hide the labels, click the toggle at the top of the sidebar, or press ⌘\ (Ctrl+\ on other systems). The sidebar then shows only icons. Put the pointer on an icon to see its name. In this state, a click on Artifacts opens the artifact list next to the sidebar. To show the labels again, click the toggle or press the same keys.

Note

When the Expert terminal has the focus, Ctrl+\ goes to the terminal, not to the sidebar. In the terminal, Ctrl+\ sends SIGQUIT to the running program. To hide or show the labels in this state, click the toggle.

Pop a pane out#

You can move a panel out of the workspace into its own browser window. This works for each service panel, Artifacts included. The agent pane stays in the workspace.

To pop a panel out, do one of these:

  • Click the Pop out button in the header of its tile, left of the close button.

  • Right-click its row in the sidebar and pick Pop out.

  • Open the command palette and run Pop out <panel>.

The panel opens in a new window the size of its tile. Its tile leaves the workspace, and its sidebar row shows a window glyph. The window follows the theme, the view and the session of the terminal. The agent can still show you the panel: a focus from the agent brings the window to the front.

While the panel is popped out:

  • A click on its sidebar row brings the window to the front.

  • Its row menu offers Bring back in place of Pop out.

  • A layout change in the workspace does not open a tile for it.

To bring the panel back, close the window, or pick Bring back from its row menu. The tile returns next to the active tile.

When you reload the terminal, the open windows stay open and connect to the reloaded page again. When you close the terminal tab, the windows stay open as normal pages, and they no longer follow the terminal.

Note

If the browser blocks pop-ups for this site, the terminal shows Pop-ups are blocked for this site. and the tile stays. Allow pop-ups for the site in the browser, then try again.

A panel that runs at an opaque origin (a page the agent wrote) cannot be popped out. Its Pop out button and row are disabled.

The More menu#

☰ More shows your user name and role at the top. It holds the View (Simple or Expert), the theme (see Theming), Settings and the tour. The same items are in both views.

Sign out#

On a multi-user deployment, the sidebar footer has a Sign out row above ☰ More. To sign out:

  1. Click Sign out. You can also click the OSPREY mark at the top of the sidebar, or pick Log out in the command palette.

  2. Read the dialog. It asks Sign out of OSPREY? and tells you that your terminal and agent sessions end, and that the agent stops what it does.

  3. Click Sign out to sign out. Click Cancel or press Escape to stay.

When you sign out, the browser goes to the landing page of the deployment. A deployment for one user has no Sign out row, and the OSPREY mark goes to the start page.

Where your preferences live#

The browser remembers the theme, the view (Expert or Simple), the sidebar labels, the open lists in the sidebar, the sidebar groups, and the panel layout. A different browser or a different machine starts from the defaults of the deployment. The browser keeps one panel layout for each view: Simple starts from one panel next to the console, and Expert starts from the full workspace.

The view is a preference. The conversation does not change with it. When you change between Expert and Simple, the same session moves to the other view. See One session, both views.

Earlier releases had a header and a status bar that you could arrange. The terminal does not show them, and it does not read the bar arrangements that those releases saved.

Documentation and feedback settings#

Five web keys aim the sidebar’s Documentation link and Feedback button — including the issue trackers the dialog offers — and bound the feedback store. The table, the shipped defaults, and what a blank value means are in web: — documentation, feedback, the bars and the chat pool.

Under the hood

Two sections in config.yml are easy to confuse. web_terminal: is the terminal process — which shell to launch, which directory to watch for live files, how many background conversations to keep alive — and command-line flags override those for a single run. web: is the browser UI the process renders, including the deployment name and the bounds on the Simple-mode chat pool; those keys are catalogued in web: — documentation, feedback, the bars and the chat pool.

One key sits outside both, in the multi-user modules.web_terminals block: modules.web_terminals.auth.session_lifetime sets how long a login cookie stays valid, in whole seconds, and defaults to 43200 (12 hours). It is the only key osprey web reads from that block.

The panels are powered by small companion servers OSPREY launches for you — an artifact gallery always, and a domain server for each enabled panel. You normally never touch them.

Every feature above is backed by a REST and WebSocket API. The endpoints are discoverable directly in the source (src/osprey/interfaces/web_terminal/); a coding agent working in the codebase can wire against them without a hand-maintained list here.
