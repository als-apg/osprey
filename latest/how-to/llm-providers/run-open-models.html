Run Open & Local Models#

Use this guide to run the OSPREY agent on open-weight and locally hostable models. It shows how to route such a model, which open models are known to work, and how to benchmark one yourself. OSPREY runs Claude Code as its agent harness, and the model behind it is a configuration choice.

Two independent axes#

  • The agent harness (the program that drives the model through tool calls) is Claude Code, the one harness OSPREY ships. Its code sits in one adapter package (Agent harness).

  • The model is a configuration choice. Any endpoint OSPREY can reach — remote or self-hosted — is set in configuration, not in code.

How open models are routed#

Open models are most often served behind an OpenAI-compatible API — that is how CBORG, Ollama, and vLLM all expose them — so OSPREY reaches them through the local Anthropic ↔ OpenAI translation proxy it starts for any OpenAI-protocol provider. How that translation works, and the routing every provider follows (diagram), are in Configure LLM Providers.

CBORG needs one extra step. The built-in cborg provider uses CBORG’s Anthropic-compatible endpoint, which serves the Claude models. Those go direct, with no proxy. CBORG’s open models live on its OpenAI-compatible side. To run one, add your own provider entry that points there; it then goes through the translation proxy like any other OpenAI endpoint.

Add the entry in providers.yml, beside the deployment’s profile.yml:

providers:
  cborg-open:
    api_key: ${CBORG_OPEN_API_KEY}
    base_url: https://api.cborg.lbl.gov/v1   # keep the /v1
    default_model: gpt-oss-120b
    models:
      - gpt-oss-120b

and in profile.yml:

provider: cborg-open

The entry names gpt-oss-120b as its default, so the profile needs no model:. The provider serves no Claude models, so the build prints one line saying Claude Code’s haiku, sonnet and opus aliases point at gpt-oss-120b.

A provider you add yourself takes its key from <NAME>_API_KEY, with the name uppercased and dashes turned to underscores. So cborg-open reads CBORG_OPEN_API_KEY. Put CBORG_OPEN_API_KEY=<your CBORG key> in the repo’s .env. The same CBORG key serves both entries.

Any model ID from CBORG’s catalogue works in the models list. The provider list and the keys behind it are in Configure LLM Providers.

For a model you serve yourself with vLLM, the packaged vllm provider is keyless and points at http://localhost:8000/v1; set VLLM_BASE_URL for a server elsewhere and list its --served-model-name under the entry’s models in providers.yml.

Which models are known to work#

These open families were verified to complete the full OSPREY end-to-end suite. For an agentic system, “runs” means sustaining a multi-step tool-calling loop across that suite, not just emitting plausible text.

  • gpt-oss (20B and 120B)

  • gemma (gemma-4)

  • cborg-coder

  • qwen-3 / qwen-3-coder

This set was chosen from the open models available on the CBORG provider — it reflects CBORG’s catalogue at benchmark time, not an exhaustive survey of open models. Capability varies widely across the set.

Benchmark it yourself#

Note

The benchmark covers an initial set of storage-ring tasks; it is not a complete assessment of open or frontier models with OSPREY. Further Tier 2 tasks and other facility types, such as free-electron lasers, are planned, and contributions are welcome.

OSPREY ships the benchmark toolchain under scripts/benchmark/ (see its README): it runs the agentic tests of tests/e2e/ — those where the model under test drives the agent — across a matrix of models and renders a per-test dashboard. The whole run is declared in one file, scripts/benchmark/matrix.yaml — each row names a provider and a model id; the launcher resolves credentials, derives the route (proxy for OpenAI-protocol models, direct for Anthropic), wires the judge, and runs one isolated worker per (model, seed) cell. Adding a model — or a self-hosted vllm server — is a config edit, not a script edit. An LLM judge, claude-haiku-5-5 on the als-apg provider, grades the answers. Each test’s agentic marker gives its tier and a plain-words description; the dashboard scores each test on its first attempt, without reruns:

# one model (substring filter), serially

# a smoke run: only the tests a pytest -k expression selects
scripts/benchmark/matrix.py --only gpt-oss-20b --select vacuum_burst --results-dir results-smoke

# the whole grid, then render the dashboard
scripts/benchmark/build_board_images.sh   # the images a full run needs, once per revision
scripts/benchmark/matrix.py --parallel 4
scripts/benchmark/matrix_dashboard.py --results-dir results --out dashboard.html
