Guarded Run Contract#

A guarded run is the lock a read-write execute or execute_file run and a pyaml_measure run hold on their control target, so two runs never drive one machine at once. No other write path takes part, except the command write, which fires only under a held lock. Guarded Runs places it among the write paths and says what it does not cover. This page is the exact behaviour: where the lock lives, who holds it, whose run its record names, what a second run is told, what a command write admits, and what a stopped run leaves.

Every write made under the lock is an ordinary write. It goes through the connector like any other, so the kill switch, the limits check and the control-target check of Safety Chain all apply to it. The lock adds no check of its own to those writes, beyond what it admits a command write on; it replaces none of them.

One run per target#

Where the lock lives#

Item

Value

Lock file

var/guarded_run/<target>/run.lock in the deployment repo

Targets

live, va, standin: one lock per target

Directory mode

0o2775 for each guarded-run directory a run creates: setgid and group-writable. var/ gets the process’s default mode, and an existing directory keeps the mode it has.

File mode

0o664 for a created lock file

Directory contents

run.lock only

The directory is deployment-wide: the deploy provisions it on the host and binds it at the same place in every container that runs the agent, so a run started from a web terminal, a dispatched job or a local osprey chat contends for the same lock. The setgid directories let every identity of the deployment sharing their group take the lock.

The lock is taken without waiting and held until the run ends. A second run on the same target, of either kind, is refused before it starts (see Refusals). A read-only run is refused before the lock is taken.

Who holds it#

Who takes the lock#

Caller

How it holds the lock

A read-write execute or execute_file run

Takes it before its code starts and releases it after its record is saved.

pyaml_measure

Runs its script through the same sandbox, so it takes the lock the same way.

pyaml_cs_osprey.run_tool, which runs every pyAML tool of a measurement

Whose run it is#

A run takes the lock with a record of whose run it is: the target it drives, the account it acts for (or nobody) and the target it was admitted on. A record whose target or admitted target is not the target the lock resolves to is refused before anything is opened, so a run is never admitted on one target and driven on another. Joining the process’s hold with no record runs under the held one; joining with a different record is refused.

The record also says whether limits checking is off for its target. That is the target’s fact, never the caller’s: it is off only when the target’s limits posture is complete and states enabled: false; silence or an unreadable limits block is not off. A record that says otherwise is refused before anything is opened.

  • A read-write execute or execute_file run fills the record once, as its sandbox starts: the stamped target, the account the write path names (nobody when it names none), that same target as the admitted one, which the executor checked before it started the sandbox, and the target’s limits posture. Nothing about the sandbox’s writes changes.

Command write#

osprey.runtime.guarded_run.command_write(connector, addresses, value) fires one value at a batch of commands (arm a monitor, request a shot) under the run lock. A command is the facility’s word, never the caller’s: a channel of the rendered facility definition whose role is setpoint and whose signal ends in command. With no rendered facility definition, no command fires.

The whole batch is refused, before anything is written, unless:

  • the process holds the run lock with a record;

  • the account the write path names is the record’s account, and the record names one;

  • the batch names each command once;

  • the connector drives the record’s target;

  • the record’s limits state is still the target’s;

  • the connector carries a limits validator that is not the fail-safe one, or limits checking is off for the target;

  • every address is a command, and passes the validator in its own mode, as a setpoint write does.

The approval of the call that leads here is its caller’s to check; a command write reads none. The batch then goes out through the connector in one call, unconfirmed, so the kill switch and the control-target check apply to it as to any write. Its phases reach osprey.runtime.record_writes as a batch write’s do, but the commands fired are the call’s own, never read back from that recorder. A channel error the batch raises names the commands of the batch not refused, which went out or may have (commands_fired). Every call, refused or not, files one audit record on the command_write surface whose detail is commands_fired=<address>,…. When the batch call itself raises, what went out is unknown: the record’s reason is outcome_unknown and its detail is commands_attempted=<address>,…, the whole batch.

The process holds it#

The lock belongs to the process, not to the thread that took it: a thread or task the run starts runs under it. Asking for the lock again from inside the process is refused like any other second run. A process holds the lock of one target at a time; asking for another target’s lock while it holds one is refused before anything is opened.

Joining a run never extends its hold: the lock is released when the code that took it ends, whatever joined it; the executor takes it for the whole script.

A forked child never holds the lock, at any moment, from any thread: a fork waits for a lock entry or release in progress to finish, and the child closes its copies of the lock. A child started with subprocess or exec never inherits it.

The lock file#

While a run holds the lock, run.lock holds its holder record, a JSON object with these keys. The record is emptied on release.

A refusal of a held target names each key, and a key reads unknown when the holder’s record does not name it.

run.lock is a regular file with one name, opened inside the target’s directory without following a link at guarded_run, at the target’s directory or at the file. A link, a hard link, a FIFO or anything else that is not such a file is refused with its path named: the run does not start, and nothing is read or written through it.

The approval prompt never opens this directory: it binds the call to its target (approved_target) and asks. Only the run refuses a held target, before its code starts and with nothing moved.

Refusals#

Each refusal is raised before the run’s code starts. In the texts, <…> stands for a value the refusal fills in. A refusal of the operating system itself (an OSError the lock file’s open raises) is passed on as it is.

What the lock does not do#

A killed or failed tool leaves setpoints where they stopped; the result lists them with their old values.

  • The lock records and restores nothing.

  • A run that is killed, fails or is interrupted leaves every setpoint where it stopped, as the MATLAB Middle Layer and pyAML do.

  • pyaml_measure lists in its result every setpoint whose write may have gone out, a write whose outcome is unknown included, with its value before the call (moved), whether the run completed, stopped or failed.

  • A run killed outright cannot list values, and its failure names the channels it attempted. That includes a run that reaches the execution timeout: nothing stops a tool early to leave time for a report, so it is killed like any other run.

  • The agent’s own Python lists nothing; its writes are in the run’s write ledger.

  • The putting back of a stepped knob inside a measurement is pyAML’s own.
