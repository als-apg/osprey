The facility.json Contract#

build/facility.json is the description’s published product: every record of the facility in one versioned document. This page is the contract between the build that writes it and every program that reads it – the panel engine, a fork of it, the framework’s own readers, or a reader in another language. What the records mean is in Facility File and Its Views; this page covers the version rules only.

Parts of the contract are not enforced yet. Each rule below says whether it holds today or is a target, and which phase of the package split makes it hold.

Producer#

The description’s build is the only producer. osprey build assembles the document and writes it to <render root>/facility.json. No other code writes the file, and no reader edits it: a reader that needs a different shape asks the build for it.

The header#

The document’s first key is its header:

{"schema": "osprey.facility.facility/3", "identity": {"...": "..."}}

The header is osprey.facility.facility/N, where N is a positive integer with no leading zero. The current version is 3; the build takes it from osprey.facility.validate.FACILITY_HEADER.

Breaking changes and the bump rule#

A change is breaking when it removes a key, renames a key, changes a key’s type, or changes what a key’s value means. A breaking change bumps N by one in the same change.

A change is additive when it only adds a key. An added key does not bump N.

Readers ignore keys they do not know. That is what makes an added key safe: a reader written against version N reads every later document at version N, whatever keys were added since.

Two consequences for a reader:

  • Never refuse a document because it holds a key you did not expect.

  • Treat a key added after the build you wrote against as optional: an older build at the same N does not have it.

The reader rule#

Every reader declares the versions it reads, as a set of complete header strings, and compares the document’s schema value against that set exactly. A document whose header is missing, malformed or not in the set is refused, and the refusal tells the user to rebuild:

build/facility.json is osprey.facility.facility/2; this reader reads
osprey.facility.facility/3 -- rebuild with osprey build

A reader does not try to read a version it did not declare, older or newer, and does not guess from the keys present. A fork that tracks the document declares the versions it has been tested against – today that is /3 – and adds a new N only after it has read that version’s breaking change.

The published schema#

The document’s shape is published as a JSON Schema generated from the description’s schema model. A test pins the generated schema: a change to the document’s shape fails that test until its author either bumps N or marks the change additive. The schema file ships inside the description package, so forks and readers outside Python can validate a document without OSPREY’s source tree.
