Errors and Logging#

The exception taxonomy callers branch on, and the logger every connector writes through. The class names and reason codes in osprey_connectors.errors are covered by the package’s compatibility guarantee.

Error classification and handling for the Osprey Framework.

Stability: the exception class names and reason codes defined here are public API. Removing or renaming any of them is a major version bump; adding new ones is a minor version bump.

This module is the connector failure vocabulary.

Three contract roots partition what a connector raises when a call fails, and no class lies under two of them: ChannelError, a failure about one named channel that leaves the connector in place; every single-channel failure (a limits violation, a refused write, a failed write, an address that is not a channel, an unreachable channel) is one, and its channel_address names the channel. ConnectorUnavailableError, the connector itself is gone and its supervisor replaces it. ConnectorInternalError, a connector bug that nothing recovers from. ChannelReadFailedError names several channels and lies under no root.

RefusalReason names why a write was refused, who refused it and what to do about it. ChannelWriteFailedError’s reason codes are the uppercased WriteOutcome words for the outcomes that raise, so the reason a caller branches on and the outcome the result reports are one vocabulary.

The connector-host IPC registry is derived from this module: every class in __all__ under a contract root crosses the process boundary as itself, with its channel, so a public failure needs no registry entry of its own.

osprey_connectors.errors.NOT_A_CHANNEL = 'not a channel of this facility'#

What an address outside the facility is, in every message that names one.

osprey_connectors.errors.RAW_CLIENT_WRITE_MARKER = 'raw client write refused'#

Shared substring of every raw-client-write refusal message. Refusals raised inside an executor subprocess reach the parent only as stderr text, so the parent recognises them by this marker; a test pins the message to it.

exception osprey_connectors.errors.ChannelError(channel_address, message)[source]#

Bases: Exception

A failure about one named channel; the connector that raised it stays in place.

channel_address names the channel, in process and across the connector-host boundary alike. No supervisor recovers from a channel error: it is reported against its channel and nothing is restarted. It has no builtin base that another root shares, so no except ConnectionError or except TimeoutError reads it as a lost connector.

commands_fired is set in process by a batch command writer when the batch raised: the addresses, in order, that may have gone out. It is None when no batch writer set it, and it is not a wire field.

Raised when an address is not a channel of the facility a connector serves.

Only a connector that holds the facility’s whole address set raises it. exception osprey_connectors.errors.ChannelReadFailedError(addresses, message=None, *, causes=None)[source]#

Bases: Exception

Raised when a batch read or a settle’s readback read could not produce a value.

A channel counts as failed when the connector’s result leaves it out (a connector drops a channel whose read raised) or reports it with the value None (the EPICS-family connectors’ answer to a read timeout).

addresses names every failed channel, each once, in the order the caller asked for them, so a caller can report or retry all of them rather than only the first.

causes maps a failed channel to the exception its own read raised, so a timeout, a refused connection and a missing channel stay distinguishable. A failed channel whose read reported no value without raising has no entry.

exception osprey_connectors.errors.ChannelWriteBlockedError(channel_address, reason, message=None, verdict_reason=None)[source]#

Bases: ChannelError

Raised when a channel write was refused and no value was written.

Distinct from ChannelWriteFailedError, which means the write was attempted and its outcome is a failure rather than a denial.

reason is a RefusalReason member when the reason is a known one, and then names its refuser and remedy. An unknown reason, or no reason at all, is kept as given and names neither: no refuser is guessed.

verdict_reason narrows WRITES_DISABLED to the reason the write verdict gave, a member of osprey_connectors.refusals.REASONS, when it gave one: switch_off, auth_exhausted, auth_range and the rest, so a program branches on the word rather than the message.

exception osprey_connectors.errors.ChannelWriteFailedError(channel_address, reason, message=None, *, outcome=None, value_written=None, observed_value=None)[source]#

Bases: ChannelError

Raised when a channel write was attempted but was not confirmed.

The control system was asked to write but the write failed, the channel now holds a different value, or the write was sent but not acknowledged in time or the confirming re-read itself failed. Distinct from ChannelWriteBlockedError (a refusal — no value was written). A scan consumer must abort on this.

reason is one of: “FAILED”, “MISMATCH”, “UNCONFIRMED” — the WriteOutcome words that raise. All three are protocol-neutral on purpose: the same codes describe an EPICS, DOOCS, or simulated write.

outcome, value_written and observed_value carry the detail the result held, so a caller that only sees the exception can still say what was sent and what the channel holds. outcome is a WriteOutcome member on either side of the connector-host boundary: the plain string the wire carries is coerced on construction, as ChannelWriteResult coerces its own.

exception osprey_connectors.errors.ClientLibraryRefusedError(*, package=None, library=None)[source]#

Bases: RuntimeError

Raised when a process that may hold no control-system client loads one.

reason is “RAW_CLIENT_IMPORT”: user code imported a control-system client package, or loaded a client shared library, in a process whose only route to the machine is osprey.runtime. Nothing was loaded and no channel was touched. package names the refused top-level package and library the refused shared library; one of the two is set.

A RuntimeError rather than an ImportError: code that treats a missing optional client as absent (except ImportError) must not read a refusal as “not installed” and carry on down another route.

exception osprey_connectors.errors.ConnectorInternalError(message, class_tag=None)[source]#

Bases: RuntimeError

Raised in the parent for something the connector-host child sent outside the contract.

It has two sources, and both fail one call only. A connector bug: the child raised an exception the IPC registry does not carry typed, and the message carries the child’s repr. An unrebuildable reply: the child answered with a value the parent cannot rebuild into its declared type. Neither is a reachability answer, and nothing about the connector or the child is implied, so no supervisor recovers from it.

It is a RuntimeError and never a ConnectionError or OSError, so that no except ConnectionError or except OSError reads a connector bug as an unreachable control system.

class_tag names the class the child sent: the exception’s class for a connector bug, the value’s class for an unrebuildable reply.

exception osprey_connectors.errors.ConnectorUnavailableError(message, recovery=())[source]#

Bases: ConnectionError

The connector itself is gone: its transport, context or process is lost.

Every channel it serves fails alike until it is replaced, and the supervisor that owns the connector’s lifetime replaces it at most once per instance. recovery is what that supervisor did, one {"action", "text"} record per step, set by the supervisor and by nothing else; it is empty until a supervisor has acted.

class osprey_connectors.errors.RefusalReason(value)[source]#

Bases: StrEnum

Why a write was refused, with who refused it and what to do about it.

Each member’s value is the reason word a result and an exception carry. refuser names who refused a write for the reason, and is None for CHANNEL_NOT_FOUND: nothing was denied, the address is not a channel. remedy holds the reason’s own suggestion sentences, in the order a message lists them; it is empty for CHANNEL_NOT_FOUND, whose answer is rendered as “not a channel”.

RAW_CLIENT_WRITE means user code called a control-system client library’s put directly instead of going through osprey.runtime.write_channel; nothing was sent. CONTROL_SYSTEM_REFUSED is the one reason under which the write was sent: the control system was asked and denied it. BATCH_REFUSED is a write of a batch that passed every check of its own and was not sent because another write of the batch was refused.

Component Logger Framework

Provides colored logging for Osprey and application components with: - Unified API for all components (capabilities, infrastructure, pipelines) - Rich terminal output on stderr with component-specific colors - Graceful fallbacks when configuration is unavailable - Simple, clear interface

Handler setup is explicit and separate from logger lookup. Entry points — the CLI, service startups, the dispatch worker, MCP servers — call configure_logging() once; everything else just calls get_logger(), which has no global side effects.

Usage:

# Entry point, once at startup configure_logging()

# Module-level logger = get_logger(“orchestrator”) logger.key_info(“Starting orchestration”)

logger = get_logger(“data_processor”) logger.info(“Processing data”) logger.debug(“Detailed trace”) logger.success(“Operation completed”) logger.warning(“Something to note”) logger.error(“Something went wrong”) logger.timing(“Execution took 2.5 seconds”) logger.approval(“Waiting for user approval”)

# Custom loggers with explicit parameters logger = get_logger(name=”custom_component”, color=”blue”)

class osprey_connectors.logger.ComponentLogger(base_logger, component_name, color='white', state=None)[source]#

Bases: object

Rich-formatted logger for Osprey and application components with color coding and message hierarchy.

Message Types: - status: High-level status updates - key_info: Important operational information - info: Normal operational messages - debug: Detailed tracing information - warning: Warning messages - error: Error messages - success: Success messages - timing: Timing information - approval: Approval messages - resume: Resume messages

Every emitted record carries the name of the method that produced it as the osprey_intent attribute, so handlers and filters can tell intents apart where the level cannot (info and key_info both log at INFO). It is metadata only: no level is remapped and no formatter reads it.

osprey_connectors.logger.configure_logging(level=logging.INFO)[source]#

Configure logging for an Osprey entry point.

Call this once, explicitly, from every entry point (CLI main, service startups, the dispatch worker, MCP server __main__). Library and import paths must never call it — importing Osprey leaves logging untouched.

The configuration is strictly additive: it installs the Osprey RichHandler only if the root logger has no RichHandler yet, and it never removes or clears handlers it did not install. Handlers owned by someone else — caplog’s capture handler, a host application’s own handlers — survive. Calling it repeatedly is a no-op beyond re-applying the level.

Parameters:

level (int) – Root logger level.

osprey_connectors.logger.get_logger(component_name=None, level=logging.INFO, *, state=None, name=None, color=None)[source]#

Get a unified logger for CLI logging.

This is a pure lookup: it mutates no global logging state. Handler and level configuration belongs to configure_logging(), which entry points call once at startup. A module that only imports Osprey therefore leaves the host application’s logging exactly as it found it.

Name the logger by its component (the recommended form), or give name and color directly for a custom or module-level logger.

Parameters:

osprey_connectors.logger.set_handler_console(console)[source]#

Render root-logger records through console from now on.

For entry points that already own a console of their own — the CLI owns the themed, terminal-sized stderr console every command prints through — so that logging and printed output share one renderer instead of interleaving two consoles with different widths on the same stream.

Deliberately separate from configure_logging(), which stays untouched: the 15+ non-CLI entry points and external consumers of this package call that and must keep the console it has always built for them.

Repointing an existing handler rather than rebuilding it keeps this safe to call any number of times in one process — CLI invocations repeat inside a single test process — with no handler ever stacking on the root logger.

Parameters:

console (Console) – Console the Rich handler should render through.

Returns:

The handler that was repointed, so a caller can go on to configure that same instance; None if the root logger has no RichHandler (a caller that has not called configure_logging() yet).

Return type:

RichHandler | None

Temporary suppression of a logger’s low-level messages.

quiet_logger() raises one or more loggers to WARNING for the duration of a with block and restores their levels afterwards.

osprey_connectors.log_filter.quiet_logger(logger_name)[source]#

Context manager to temporarily suppress INFO-level messages from logger(s).

This is a convenience wrapper around _suppress_logger_level() that specifically suppresses INFO and DEBUG messages while preserving WARNING, ERROR, and CRITICAL. This is the most common use case for “quiet” operations.

Parameters:

logger_name (str | list[str]) – Name of logger(s) to quiet. Can be a single string or list of strings for multiple loggers.

Yields:

Dictionary mapping logger names to their original levels

Examples

Quiet a single logger:

>>> with quiet_logger('registry'):
...     initialize_registry()  # No INFO messages shown

Quiet multiple loggers:

>>> with quiet_logger(['registry', 'DATABASE']):
...     do_something()

Note

This raises the level to logging.WARNING for the block.
