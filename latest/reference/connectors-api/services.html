Directory, alarms and put log#

The read-only contracts of the directory, alarm and put-log backends behind All PVs (All PVs: the Control System’s Directory), and which source answers each kind on each control target.

What every read-only service backend answers, whatever its kind.

A backend is read-only and never raises: a service that gives no answer is a value, Unavailable, or a page whose outcome says so. Every method is async and takes deadline, the seconds this call may spend; the caller owns the overall budget and hands the same figure to calls it runs concurrently.

Backends are built as Backend(spec, *, project_dir=None, **seams). The constructor does no I/O and there is no connect step, so building one answers nothing about the service; probe does. Out-of-tree classes follow the same signature. A seam the class does not take is ignored, because the factory passes the same keywords to every backend of a kind.

The records stay plain so one conversion makes their JSON: a list, a mapping or a string stays what the service answered, as the service recorded it.

class osprey_connectors.alarm_state.AlarmState(spec, *, project_dir=None, **seams)[source]#

Bases: _Backend, ABC

Follow a live alarm feed.

start() begins whatever feeds the snapshot and aclose() ends it; both are idempotent. Until the feed has caught up, reads answer Unavailable("alarm feed still loading"), and once caught up with no message at all, Unavailable("no message from the feed yet"): never a clear state and never in_tree: "no". A read of a started feed waits for catch-up up to its deadline and only then answers alarm feed still loading; a feed that already knows its answer, unreachable or unbuildable, answers at once.

Which source answers each directory section on each control target, in one place.

A deployment carries one pv_directory: block and a session can be pointed at up to three machines. A section answers only from the machine the session is on, so service_targets() says which source that is per target, and a reader holding None says “not available for this target”: never another machine’s data under the selected machine’s name.

row

va

live and standin

directory

simulator_view when simulator.has_simulator

the section’s type

alarm_state

alarm_replay when replay_file is set

the sub-block’s type

alarm_log

None

the sub-block’s type

put_log

None

the sub-block’s type

The facility’s services belong to the facility’s machine and the stand-in rehearses that machine, as osprey_connectors.archive_targets has it, so the two share APPLIANCE_TARGETS and a standin spec is marked rehearsal. A simulator spec carries none of the facility’s settings, and a facility spec no replay_file. replay_file is passed verbatim: only the framework reads its demo: spelling.

Pure, and never raises: the answer is a function of the mapping alone. A block that is not a mapping, or a type or replay_file that is not a non-blank string, names no source; refusing such a block at build is resolve_section’s job in the framework.
