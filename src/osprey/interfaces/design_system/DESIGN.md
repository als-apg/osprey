# OSPREY Design System — Designer Handoff

This is the contract between the token source and every browser interface OSPREY
ships (Web Terminal, Artifacts, ARIEL, Channel Finder, Lattice dashboard, the
event-dispatch dashboard, the KNOWLEDGE panel, and the session/safety pages).
Read this before touching a token file or a `.css` file in an enforced interface.

## 1. What lives where

| Path | What it is |
|---|---|
| `tokens/core.json` | Theme-independent primitives: the fourteen color families — ten fleet-wide (`slate`, `gray`, `mono`, `teal`, `azure`, `amber`, `red`, `green`, `blue`, `violet`) and four owned by the `desy` family (`cyan`, `orange`, `petrol`, `desy`) — plus `font` and the `text`/`weight`/`leading`/`space`/`radius`/`z`/`duration` scales. Colors are **never** emitted as CSS variables directly — themes and interfaces reference a color step one hop away via `{color.family.step}` aliases. |
| `tokens/themes/*.json` | One file per theme (8 today). Each aliases `core.json` primitives into semantic names (`bg.primary`, `text.secondary`, `accent.base`, ...). |
| `tokens/interfaces/*.json` | Per-interface extension tokens (`ariel.json`, `artifacts.json`, `channel_finder.json`, `lattice_dashboard.json`, `web_terminal.json` today) — values an interface needs that aren't fleet-wide semantics. |
| `generator/` | The build pipeline: `model.py` (load/parse), `validate.py` (fail-closed checks), `emit_css.py`/`emit_js.py` (renderers), `build.py` (orchestrator + CLI + `--check`). |
| `static/css/tokens.css`, `static/js/tokens.js`, `static/js/theme-boot.js` | **Generated. Never hand-edit.** Regenerated by the one command below; a stray manual edit is overwritten (and CI's `--check` will flag the drift anyway). |
| `static/css/base.css` | Hand-maintained shared reset + primitive element defaults (`html`, `body`, scrollbars, the theme-transition rule) and the handful of chrome components every interface draws identically: the pane splitter (`.osprey-splitter`), the info tip (`.osprey-info` / `.osprey-tip` — the "?" disc with a hover/focus bubble) the right-click menu (`.osprey-context-menu`, opened by `js/context-menu.js`) and the column grips of a movable, resizable table (`.col-resize`, driven by `js/table-columns.js`). Every browser interface loads this after `tokens.css`. Contains zero color literals and no app-specific selectors. |
| `static/css/primitives.css` | Hand-maintained shell primitives (sidebar rows, list rows, popovers, tooltip, buttons, status dots, inset card, pane header) — see §9. Loaded after `base.css`; same rules: tokens only, no app-specific selectors. |
| `static/js/icons.js`, `popover.js`, `tooltip.js`, `collapsible.js`, `sidebar-boot.js` | The behaviour that goes with `primitives.css` — see §9. `sidebar-boot.js` is a non-module pre-paint script like `mode-boot.js`. |
| `static/reference.html` | The live token reference page — see §8. |

## 2. The one command

```
python -m osprey.interfaces.design_system.generator.build
python -m osprey.interfaces.design_system.generator.build --check
```

Without `--check` it loads `tokens/`, validates it, and (re)writes the three
generated artifacts. With `--check` it does the same load-and-render but never
writes — it diffs the result against what's on disk and exits non-zero with a
unified diff on any drift. **CI runs `--check`**, so regenerate in the same
commit as any edit under `tokens/`.

## 3. The levers

Every family below is emitted once, at `:root`, and is theme-independent — no
theme can override a `--text-*`/`--weight-*`/etc. value.

| Family | Variable prefix | Steps | Enforcement |
|---|---|---|---|
| Type scale | `--text-*` | `2xs` 8px, `xs` 9px, `sm` 10px, `base` 11px, `md` 12px, `lg` 13px, `xl` 14px, `2xl` 16px, `3xl` 18px, `4xl` 32px | Strict |
| Weight | `--weight-*` | `regular` 400, `medium` 500, `semibold` 600, `bold` 700 | Strict |
| Leading | `--leading-*` | `none` 1, `tight` 1.3, `snug` 1.4, `normal` 1.5, `relaxed` 1.6, `loose` 1.7 | Strict |
| Radius | `--radius-*` | `none` 0, `xs` 2px, `sm` 3px, `md` 4px, `lg` 6px, `xl` 8px, `2xl` 12px, `full` 9999px | Strict |
| Duration | `--duration-*` | `instant` 120ms, `fast` 150ms, `base` 200ms, `slow` 300ms | Strict |
| Spacing | `--space-*` | `0`–`8`, 0px to 64px (4px-based) | Preferred only |
| Z-index | `--z-*` | `base` 0, `dropdown` 100, `sticky` 200, `overlay` 300, `modal` 400, `toast` 500 | Preferred only |
| Fonts | `--font-display`, `--font-mono` | `'Outfit', system-ui, sans-serif` / `'JetBrains Mono', monospace` | Strict |

"Strict" means the hygiene scanner (§5) fails the build on a bare literal in an
enforced interface's `.css`; "preferred only" (spacing, z-index) means the
variable is the recommended spelling for new code but nothing fails if you
write `margin: 16px` — spacing literals are far denser than the other
properties across existing CSS, and z-index frequently encodes legitimate
intra-component micro-stacking a shared scale can't cleanly express.

**Naming caveat:** step names reflect *observed frequency* in the CSS that was
migrated onto this scale, not a designer's judgment about what "base" should
mean. `--text-base` is 11px because 11px was the most common unlabeled
font-size in web-terminal's CSS at migration time — not because 11px is
considered a canonical body size. Renaming a step (or moving where a value
sits on the scale) is a legitimate design decision; make it in `core.json`
and rebuild — never rename by find-and-replace in the generated CSS.

## 4. Themes

Eight themes, four families × two modes:

| Family | Dark | Light |
|---|---|---|
| `main` (default) | `dark` | `light` |
| `high-contrast` (WCAG AAA, fully monochrome) | `high-contrast-dark` | `high-contrast-light` |
| `retro` (pre-redesign navy/teal) | `retro-dark` | `retro-light` |
| `desy` (DESY corporate palette) | `desy-dark` | `desy-light` |

`high-contrast` is `main` with every hue removed: it resolves entirely onto
the achromatic `color.mono` ramp, including status, diffs, chart series and
the ANSI palette, so state separates by lightness rather than color. That is
a deliberate constraint, not an omission — a value added there in green or
amber is a bug. The interface extension files (`tokens/interfaces/*.json`)
therefore author their own `high-contrast-*` groups rather than inheriting
the chromatic ones; see §4's `inherits` note below.

`retro` changes colors only: the sidebar shell has one layout for every
family.

A theme is selected by the `data-theme="<id>"` attribute on `<html>`, applied
pre-paint by `theme-boot.js` to avoid a flash of the wrong theme. The theme
flagged `$extensions.default: true` (currently `dark`) doubles as the `:root`
fallback for any page that never sets `data-theme`.

An interface's extension tokens (`tokens/interfaces/*.json`) can opt a theme
out of authoring its own group via `$extensions.inherits`, e.g.
`{"retro-dark": "dark"}` — the interface then borrows its `dark` group's
values for `retro-dark` instead of duplicating them. This is for interfaces
whose extension values genuinely don't vary across those themes (a font
stack, a layout constant, a decorative accent the theme doesn't touch).
`high-contrast-*` is deliberately never inherited from a chromatic group:
that family is monochrome, so an inherited value is how a stray hue gets in.

**To add a theme:** add a new JSON file under `tokens/themes/` with the same
semantic key set as an existing theme of that mode (the validator enforces
key-set parity), give it a `family`/`mode`/`id`/`label` in `$extensions`, then
run the build command. No code changes are needed to wire it into the theme
switcher — it's discovered from the token tree.

Theme switching is entirely client-side (`theme-manager.js`): no server round
trip, no page reload.

Chart colors cross into JS only through `theme-manager.js`'s computed-style
bridges: `chartTheme()`/`chartSeries()` build a Plotly layout fragment and
categorical palette from the `--chart-*` tokens, and `chartRelayout(gd)`
builds the flat relayout update that re-themes an already-plotted figure in
place — including 3D scenes (box, axis panes via `--chart-pane-bg`, grids,
spikes) and only for the subplots the figure actually has. The artifact
gallery's served Plotly pages and its timeseries charts both apply exactly
this, so a plot re-themes identically whether it was just rendered or is
being flipped live, and no page carries a palette of its own.

### Surface tokens

Every theme defines a `surface` group (emitted as `--surface-*`) for the
sidebar shell: a canvas, raised cards on it, a well inside a card, and the
washes that mark state on those surfaces. Use these instead of picking a
`--bg-*` token by hand: the `bg.*` steps do not keep the same depth order in
every theme (in `desy-light` and `retro-light`, `bg.panel` is darker than
`bg.primary`), the surface group does.

| Token | Use | Value rule |
|---|---|---|
| `--surface-canvas` | Page canvas under the cards; the sidebar sits on it | Dark: the `bg.primary` step. Light: the `bg.secondary` step. |
| `--surface-card` | Pane cards, popovers | Dark: the `bg.panel` step. Light: the `bg.terminal` step. |
| `--surface-well` | Recessed area inside a card | A step between canvas and card (normally `bg.terminal` in dark, `bg.primary` in light) |
| `--surface-hairline` | Card and divider borders | `border.default` at 0.8 alpha (a border that is already alpha keeps its own) |
| `--surface-hover` | Hover wash | `text.primary` at 0.06 |
| `--surface-press` | Pressed or open wash | `text.primary` at 0.10 |
| `--surface-selected` | Selected row wash | `accent.base` at 0.12 |
| `--surface-focus` | Focus halo (`box-shadow: 0 0 0 3px`) | `accent.base` at 0.28 |

Canvas, card and well per theme. In every theme the canvas is the deepest and
the card the most raised:

| Theme | Canvas | Well | Card |
|---|---|---|---|
| `dark` | `gray.950` | `gray.900` | `gray.850` |
| `light` | `gray.150` | `gray.100` | `gray.50` |
| `desy-dark` | `petrol.950` | `petrol.900` | `petrol.850` |
| `desy-light` | `petrol.150` | `petrol.50` | `desy.white` |
| `retro-dark` | `slate.1000` | `slate.950` | `slate.900` |
| `retro-light` | `slate.300` | `slate.150` | `slate.50` |
| `high-contrast-dark` | `mono.1000` | `mono.950` | `mono.900` |
| `high-contrast-light` | `mono.100` | `mono.50` | `mono.0` |

Two wells leave the normal rule: `retro-dark`'s `bg.terminal` is deeper than
its canvas and `high-contrast-dark`'s equals it, so both use the step between
canvas and card. The high-contrast washes are pure white or black alphas, as
the rest of that family. The WCAG gates still measure text on `bg.primary`
only; text on a card is not gated.

The shell's sizes are web terminal interface tokens, identical in all eight
groups of `tokens/interfaces/web_terminal.json`: `--wt-sidebar-width` (232px),
`--wt-sidebar-collapsed-width` (56px), `--wt-pane-head-height` (40px),
`--wt-gutter` (8px) and `--wt-ease-out` (the ease-out curve for sidebar and
disclosure motion; pair it with a `--duration-*` token).

## 5. Hygiene rules

Enforced by `tests/interfaces/design_system/test_hygiene.py`, which scans
every `.css`/`.js`/`.html` file under `src/osprey/interfaces/` (plus the
dispatch dashboard):

- **Hardcoded colors — fleet-wide, zero tolerance.** No hex or `rgb()`/`hsl()`
  literal is allowed anywhere in scope. A genuine, permanent exception (a
  print stylesheet, a fixed categorical hue with no token equivalent) gets a
  trailing `/* hygiene-allow-color: <reason> */` comment, or a
  `hygiene-allow-color-start`/`-end` block around a multi-line span.
- **`var()` reference integrity.** Every `var(--name)` must resolve to a
  generator-emitted name or a name declared locally within the same
  interface.
- **No stray token-defining blocks** outside `design_system/static/` — a
  `:root {}` or `[data-theme=...] {}` block may not redeclare a name
  `tokens.css` already emits.
- **Scale literals — scoped, zero tolerance.** A bare `font-size`,
  `font-weight`, `line-height`, `border-radius` (and its longhands), or
  `transition`/`animation` duration literal is forbidden in any `.css` file
  belonging to an interface in `SCALE_ENFORCED_INTERFACES` (`web_terminal`,
  `design_system`, and `ariel`). A deliberate exception gets a trailing
  `/* hygiene-allow-scale: <reason> */` comment. Four reasons are in active
  use today: `off-scale legacy value, designer to rationalize` (a value with
  no matching scale step, left for a designer to decide whether to fold onto
  the scale or keep as a one-off); `decorative animation timing, not
  interaction-transition scale` (keyframe animation timing, which is a
  different design concern than the `--duration-*` scale's interactive
  transitions); and two one-offs in `design_system/static/css/highlight.css`
  (`deliberate slow decay`, `reduced-motion hold`) for the agent-flash
  timings, which are a stated behavioral contract rather than scale steps.

**Scanner reach:** the scale check (d) only parses `.css` files and only the
listed longhand/shorthand property names — a `font:` shorthand declaration or
a scale-shaped literal in a `.js`/`.html` file passes through it unseen. For
ARIEL that blind spot is closed by a second, interface-specific check:
`test_ariel_scale_layer_stays_retired` (check (e)) scans ARIEL's `.js` files
for `font-size`/`font-weight`/`border-radius` literals *inside string
literals* — the inline `style=`/`cssText` strings check (d) cannot reach —
and ARIEL's `.css` files for *definitions* of the retired
`--ariel-(text|space|radius|leading|z)-*`/`--transition-*` names (check (d)
reads declaration values, never the names being declared). No equivalent
check exists for `web_terminal` or `design_system`. Running check (e)'s JS
scanner over them by hand today reports zero hits — the shared components'
injected stylesheets were tokenized as part of the ARIEL parity work, which
is where the last few (`<osprey-theme-switcher>`'s own `border-radius` and
`font-size` literals) came from. But nothing enforces that for them, and the
blind spot is wider than what check (e) closes: a `font:` shorthand, and the
scale properties no JS-side check scans at all, still pass everywhere. For
those two interfaces this remains a known scope limit rather than a known
gap. Check (e) is the template to copy when the next interface on-ramps —
see §6, step 4.

## 6. On-ramping an interface onto the fleet scales

An interface is "on-ramped" when its CSS reads the emitted `--text-*`,
`--weight-*`, `--leading-*`, `--radius-*` and `--duration-*` variables instead
of a parallel local scale, and check (d) is switched on to keep it that way.
ARIEL is the worked example throughout this section: it was the first follower
after the two original interfaces, and every claim below is something its
migration actually did. `channel_finder` followed it, retiring its type,
radius, transition and spacing scales (check (e2) guards them); its spacing
mapped by value with one off-scale step, 20px, rounded down to `--space-4`
as ARIEL's did. The remaining siblings — `artifacts`,
`okf_panel`, `lattice_dashboard` — still define their own local,
interface-prefixed scales (`--art-*`, `--okf-*`, `--ld-*`) and are the next
followers. A brand-new standalone service has no local scale to
retire, so steps 1 and 2 are empty for it — it reads the fleet variables from
its first line of CSS and starts this playbook at step 3.

### Step 1 — Build the mapping table BY VALUE, before touching any CSS

Local scale names look like fleet names and mean different things. Resolve
every local step to its pixel value, then map it to the fleet token that
*has that value* — never to the token with the matching suffix. In ARIEL's
case the suffixes were off by roughly one step for the whole spacing ramp:

| Local step | Resolves to | Fleet token | Value | Note |
|---|---|---|---|---|
| `--ariel-text-base` (body) | 16px | `--text-xl` | 14px | −12.5%: the fleet body default |
| `--ariel-text-3xl` (h1) | 30px | `--text-4xl` | 32px | +7% |
| `--ariel-text-2xl` (h2) | 24px | `--text-3xl` | 18px | **no neighbor** — see below |
| `--ariel-text-xl` (h3) | 20px | `--text-2xl` | 16px | −20% |
| `--ariel-text-lg` (h4) | 18px | `--text-xl` | 14px | lands at body size; differentiated by `--weight-semibold`, the web-terminal idiom for minor headings |
| `--ariel-space-6` | 24px | `--space-5` | 24px | same value, **different suffix** |
| `--ariel-space-8` | 32px | `--space-6` | 32px | same value, different suffix |
| `--ariel-space-5` | 20px | `--space-4` | 16px | **no neighbor** — rounded down; see below |
| `--transition-fast` | `150ms ease` | `var(--duration-fast) ease` | 150ms | the duration is the token; the easing keyword stays literal |

A row with no neighbor on the fleet scale needs an explicit, up-front design
decision rather than a lookup, and those rows are the reason this table is
built before the edit rather than discovered during it. ARIEL had two, one on
each scale, and they are worth reading together — the type one had no choice
about *whether* to join the scale, only about which step; the spacing one
could have declined the scale entirely and chose not to:

- **No neighbor on the type scale.** The fleet scale jumps 18px (`--text-3xl`)
  straight to 32px (`--text-4xl`), so ARIEL's 24px h2 had nothing to land on.
  Rounding *up* to 32px would have made h2 and h1 the same size; the decision
  was to round down to 18px — a deliberate 25% reduction that compresses the
  whole heading ladder, and the single largest visual change in the migration.
  That is a judgment call, and it belongs in the plan and the PR description
  where a reviewer can accept or reject it, not in a commit that reads as
  mechanical.
- **No neighbor on the spacing scale.** The spacing ramp is 0, 4, 8, 12, 16,
  24, 32, 48, 64 — there is no 20px step, so ARIEL's `--ariel-space-5` (20px)
  had nothing to land on either. Unlike a font size, a spacing value is
  allowed to stay a literal (see the next bullet) — so this was a real fork,
  and the restyle chose the scale: standalone `padding: var(--ariel-space-5)`
  became `var(--space-4)` (16px), and the `--ariel-space-4`/`--ariel-space-5` pairs
  (16/20px) became `var(--space-3) var(--space-4)` (12/16px). That is a
  deliberate density tightening across every card, panel and input, and it is
  the same class of judgment call as the h2 decision: it belongs in the PR
  description where a reviewer sees it, not buried in a diff.
- **Spacing literals are nonetheless legal.** Spacing and z-index are
  "preferred only" (§3) — check (d) never looks at `margin`/`padding`/`gap`
  or `z-index` even in an enforced interface. So a genuinely off-scale
  spacing value may simply stay a literal, and one does: the
  `padding-right: 128px` at `ariel/static/css/components.css:179` reserving
  clearance for the button cluster inside the search input. That is not debt.
  It is a measurement of a specific piece of chrome, and no step on a shared
  ramp expresses it more honestly. Round onto the scale when the value is
  ordinary layout rhythm; keep the literal when it is a measurement.

Values that map cleanly need no decision, but they still need to be *in* the
table: it is what makes the migration reviewable as a list of intended
changes rather than a diff to be read line by line.

### Step 2 — Land definitions, usages, and guard enrollment in ONE commit

Check (b) (`test_var_integrity`) pools every locally-declared custom-property
name per interface and requires each `var(--name)` to resolve against that
pool plus the generator-emitted names. So deleting the local `:root` block in
one commit and rewriting its call sites in the next leaves every intervening
commit red — the references dangle in between. Migrate the definitions, all
their usages, and the guard enrollment (step 4) together.

### Step 3 — Migrate JS inline styles BY RULE, not by enumeration

Interfaces that build markup in JavaScript carry scale and color literals
inside `style=` attributes and `cssText` strings. Migrate them by a rule you
can state and re-apply, because an enumeration built by hand goes stale:

- **Every `font-size`, `font-weight`, and `border-radius` literal migrates**
  to a token. These are exactly the three properties an ARIEL-style JS guard
  (step 4) can see, so once migrated they stay migrated.
- **Spacing stays exempt**, mirroring check (d) in CSS.
- **Named colors are invisible to every guard.** The color regex (check (a))
  matches only hex, `rgb()`/`rgba()`, and `hsl()`/`hsla()`; `black`, `white`,
  `silver`, `red` and the rest of the CSS named colors pass all of them
  untouched, forever. There is no automated inventory to run — read the files
  and list them by hand. A keeper gets a comment saying why, because nothing
  else will ever ask again. ARIEL's one surviving set is the image lightbox
  (`ariel/static/js/entries-detail.js:246-275`): a scrim is conventionally
  dark whatever theme the page is on, so its backdrop and caption use
  `black`/`silver`/`white` composites rather than themed tokens that would go
  light-on-light. The justification comment sits directly above the
  `cssText` it explains. Note that it needs no `hygiene-allow-color` marker —
  there is nothing to suppress, since no check ever fires on it. The comment
  is the entire control.
- CSS-wide keywords (`inherit`, `none`, `transparent`) are not literals of
  anything and stay as they are.

### Step 4 — Enroll in the guards

Add the interface's directory name to `SCALE_ENFORCED_INTERFACES` in
`tests/interfaces/design_system/test_hygiene.py` — that switches on check (d)
for its `.css` files with zero tolerance.

Then write the interface's own definition-and-JS guard, modeled on check (e)
(`test_ariel_scale_layer_stays_retired`, same file). Check (d) structurally
cannot express either half of what check (e) adds: it reads declaration
*values* in `.css` files, so it sees neither a re-declaration of a retired
scale name nor anything at all inside a `.js` file. Copy the shape:

- a definition regex over the retired local families, run against the CSS
  with comments stripped (prose recording a value's old spelling must not
  count as a definition);
- a `var(--<prefix>-...)` reference regex over the JS, with a negative
  lookahead for any sanctioned generator-emitted extension tokens sharing the
  prefix — ARIEL's `--ariel-score-*` badge colors are declared in
  `tokens.css` like any other token and are exempt everywhere;
- the inline-style literal scan, which runs over a *masked* copy of the JS in
  which everything outside a string literal is blanked out
  (`_mask_non_string_regions`). The mask is what makes "inside a string
  literal" real: a comment mentioning `font-size: 12px` is not an inline
  style, and a regex literal containing a lone quote must not open a string
  and desynchronize the rest of the file.

Only the third prohibition carries a `hygiene-allow-scale` escape. The first
two have none, deliberately: a retired name always has a fleet spelling to
migrate to. On the migrated ARIEL tree the whole check passes with zero
exemptions.

### Step 5 — Mount `<osprey-display-menu>` in the standalone header

`design_system/static/js/components/osprey-display-menu.js` is the shared
settings popover: one faders button collapsing Appearance (light/dark), View
(Expert/Simple) and Theme (family pills) behind a card, plus an optional
Settings entry and a projected action slot. Every standalone surface mounts
it — the web-terminal hub, ARIEL, artifacts, channel_finder, okf_panel and
lattice_dashboard — so a new interface copies any of them.

- Import it for its side effect
  (`import '/design-system/js/components/osprey-display-menu.js';`) and place
  `<osprey-display-menu>` in the header. Add
  `settings-drawer="<drawer-id>"` if the page has an `<osprey-drawer>` — the
  attribute renders a Settings button carrying `data-drawer`, which is the
  delegated trigger `<osprey-drawer>` already installs document-wide. The
  component neither imports nor needs the drawer module.
- Select the theme role off the embed state:
  `initTheme({ role: isEmbedded() ? 'follower' : 'hub' })`, with
  `isEmbedded()` imported from `frame-params.js` (it answers from the URL, so
  the call needs no particular ordering against `applyEmbedded()`). That one
  expression is the only theme-related change an on-ramping page makes:
  persistence, OS auto-follow and `?theme=` handling all come with the hub
  role, and broadcast is a structural no-op on a page with no iframes.
  `theme-manager.js` itself is untouched.
- **Add no page CSS for the embedded case.** The component injects both its
  own skin and the `body.embedded osprey-display-menu { display: none; }`
  rule itself, once per page however many instances mount
  (`_ensureStyleInjected`). An interface that had a hand-written
  `body.embedded osprey-theme-switcher` hide rule retires it along with the
  switcher.
- **Page-owned chrome goes into the action slot.** Element children written
  inside the tag are moved into the card's action row after the three
  preference rows; the hub projects its Settings (keeping the
  `data-drawer-trigger` gate contract) and Log out buttons this way. The
  component attaches no behavior to projected children — a page that wants
  the card dismissed calls `closeMenu()` on the element itself.
- Preferences are origin-scoped and deliberately shared across surfaces: a
  theme or view pick made on a standalone panel *is* the operator's
  preference, and the hub adopts it on next load. Embedded panels are
  insulated by the `?theme=`/`?mode=` query parameters, which outrank storage.

### What legitimately stays local

The enforced invariant is narrower than "no local custom properties." A local
custom property is fine as long as it (1) does not duplicate a name
`tokens.css` emits — check (c) — and (2) resolves within its own interface —
check (b). Prefixing is a remedy for an *actual* collision, not a standing
requirement.

ARIEL's `:root` block in `ariel/static/css/base.css` is what a legitimate
survivor looks like: status-tint and shadow composites built with
`color-mix()` from canonical color tokens (so they still theme correctly),
the layout dimensions (`--container-max`, `--sidebar-width`,
`--header-height`), and the letter-spacing scale `--tracking-tight` /
`--tracking-normal` / `--tracking-wide`. The `--tracking-*` names are
**unprefixed and legal**: no fleet tracking token exists, so there is nothing
to collide with and check (c) cannot fire. If a fleet `--tracking-*` ever
ships, check (c) fails at that moment and forces the migration then — which
is the right time to do it, not now.

### Known follow-ups

The popover now exists in exactly **one** implementation. The hub's own copy
(`web_terminal/static/js/display-menu.js` and the `.display-menu-*` block in
`terminal.css`) is gone: the hub mounts `<osprey-display-menu>` with its
Settings and Log out projected into the action slot, and keeps only a
tag-scoped remainder in `terminal.css` for the Log out skin. `modeOf(id)`
lives in `theme-manager.js` beside `familyLabel`/`themeFamilies`, and both
components import it. The `display_menu` DocShot recipe
(`docs/screenshots/recipes.py`) photographs the open card on `channel_finder`.

What is left, in order:

1. *Optional tidy-up:* cap the component's mode listener at one per page.
   Each instance registers its own `onModeChange()` callback and
   `onModeChange()` has no unsubscribe, so N instances leave N listeners
   bound for the life of the page. A module-level registration dispatching
   to a static `Set` of instances would fix it. Harmless today (one instance
   per page, and the callback is a pure UI sync).
2. `<osprey-theme-switcher>` now has one consumer, `web_terminal`'s
   `session.html`, plus `static/reference.html`. It stays a shipped component
   for as long as that page mounts it; retiring it means giving session.html
   the display menu too.

Worth doing whenever the file is next open: reword the `var(--…)` prose in
`components/osprey-theme-switcher.js`'s module docstring (line 52). That
docstring is the exemplar every new component is copied from, and its literal
ellipsis placeholder false-positives check (b)'s balanced-paren extraction —
which is why `_KNOWN_DANGLING_VARS` carries an entry for a custom property
named `…` that does not and cannot exist. Spelling the sentence differently
removes both the allowlist entry and the pattern new components inherit.

## 8. Preview

`static/reference.html` renders every emitted token — colors, type scale,
fonts, weights, leading, spacing, radii, durations — plus a few composed
specimens (button, badge, card, status pills), all read live off the page's
computed `:root` styles at runtime. There's no hardcoded token list in the
page; add a token to `core.json`/a theme, rebuild, and it shows up
automatically. It includes the `<osprey-theme-switcher>` element, so you can
flip through all eight themes in place. The "Shell primitives" specimen shows
the §9 primitives on the surface tokens, with the real popover, tooltip and
collapse behaviour (its toggle uses its own storage key).

It's served by every interface's shared static-mount helper at
`/design-system/reference.html` — with a Web Terminal (or any other
interface) running locally, open `http://localhost:<port>/design-system/reference.html`.

## 9. Shell primitives

`static/css/primitives.css` holds the chrome vocabulary of the sidebar shell.
Copy these classes; do not restyle a local copy. Every value comes from the
surface tokens (§4) and the scales (§3). State always has a shape as well as
a hue (a bar, an outline, a knob position, a check mark), because the
high-contrast themes have no hue.

| Class | What it is |
|---|---|
| `.osprey-ic` | 16 × 16 Lucide stroke icon (stroke width 1.75, `currentColor`); built by `icon(name)` in `icons.js` |
| `.osprey-icon-btn` | 28 × 28 icon button: hover and press washes, `[aria-expanded="true"]` pressed, `:disabled` at 0.35 opacity |
| `.osprey-btn`, `.osprey-btn.primary`, `.osprey-btn-label` | 28 px text button in the display font; `.primary` fills with the accent; put the text in `.osprey-btn-label` so a narrow container can hide it |

| `.osprey-section-label` | 24 px group heading |

The JS modules (ES modules unless noted; each has a `.test.mjs` in
`tests/interfaces/design_system/`):

| Module | API | Behaviour |
|---|---|---|
| `icons.js` | `icon(name, {size})`, `ICON_NAMES` | Builds an `svg.osprey-ic` with `createElementNS`; throws on an unknown name. Lucide paths (ISC licence, text in `web_terminal/static/js/LUCIDE-LICENSE.txt`); `agent` and `bash` are OSPREY's. |
| `popover.js` | `openPopover(pop, anchor, {place, edge})`, `closePopover(pop)`, `closeAllPopovers(except)`, `togglePopover(opener, pop, opts)` | `place`: `beside-right`, `beside-right-bottom` (8 px right of `edge` or the anchor, clamped inside the window) or `below-end` (4 px under, right-aligned). Sets the opener's `aria-expanded` and `aria-controls`, focuses the first item, and gives focus back to the opener when a close takes it away. In a `role=menu` popover ArrowUp/ArrowDown (wrapping), Home and End move between the enabled items. Closes on a press outside, Escape, resize and window blur. A popover opened from inside another keeps its parent open. |
| `tooltip.js` | `initTooltips(root, {when})`, `hideTooltip()` | Shows `data-tip` beside a `[data-tip]` element in `root` on hover and focus, while `when()` is true and the element's `aria-controls` popover is closed. |
| `collapsible.js` | `initCollapsible({attribute, storageKey, toggle, controls, shortcut})` → `{isCollapsed, toggle, set}` | State on `<html>[attribute]` (`collapsed` or `expanded`; absent = expanded). The toggle button carries `aria-expanded` (true while the labels show) and `aria-controls` (`controls`, default `sidebar`) with a label that flips between Hide and Show. The button, Cmd+\ (macOS) or Ctrl+\ and `set()` change the state; it is stored under `scopedStorageKey(storageKey)` and announced as `osprey-collapsible-change` `{attribute, state}` on `document`. |
| `sidebar-boot.js` | none (non-module pre-paint script) | Stamps `data-sidebar="collapsed"` on `<html>` from the scoped `osprey-sidebar` key, so the sidebar never flashes the other width. Same inline scope rule as `mode-boot.js`; no fallback to the bare key on a scoped page. |
