`osprey facility validate` reports two limits findings on stderr: the setpoints with no limits record, which the target serves writable with no range when its limits mode is `optional` and refuses otherwise, and the limits records that serve their setpoint not writable, each with what it lacks: a missing `min_value` or `max_value` on a float or int setpoint, `writable: true` on any other. Each finding is a count line and its addresses, the first ten unless `--all-limits` is given. The findings change nothing: what is served and the exit code stay as they were. A re-import beside an existing `limits.yaml` now names the setpoints the export bands that the file has no record for (a count and the first ten), and writes none of them; and it names each per-device `Range` table whose row count is not the family's device count, from which no band is taken.
