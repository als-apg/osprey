===============================
Hello World Tutorial
===============================

Build and run your first OSPREY agent in about five minutes, with no containers
and no hardware. The ``hello-world`` preset is the smallest deployment that
still shows the whole write-safety chain: a mock control system that invents
channel values, ten safety and bookkeeping hooks, and a browser interface.

Three ``osprey`` commands take you from nothing to a running agent:

.. code-block:: bash

   osprey init my-first-agent --preset hello-world
   cd my-first-agent
   osprey build
   osprey web

The rest of this tutorial walks that path slowly, because the point is not the
agent — it is the ``profile.yml`` you get along the way, which doubles as the
syllabus for everything OSPREY can grow into.

.. dropdown:: **Prerequisites**
   :color: info
   :icon: list-unordered

   **Required:**

   - Python 3.11+
   - `Claude Code <https://docs.anthropic.com/en/docs/claude-code/overview>`_ CLI installed
   - Osprey framework installed (``uv tool install osprey-framework``, or
     ``uv sync --extra dev`` if working from a clone)
   - ``ANTHROPIC_API_KEY`` set in your environment

   If you haven't installed the framework yet, follow the :doc:`installation guide <installation>`.

Step 1: Create the Project
---------------------------

.. code-block:: bash

   osprey init my-first-agent --preset hello-world
   cd my-first-agent

``osprey init`` writes one git repository. Everything the preset configures is
spelled out in files you own — nothing is hidden or inherited:

.. code-block:: text

   ✓ Created my-first-agent

     profile.yml   your assistant's settings; edit this
     data/         channel lists and facility docs; edit these
     .env          from your shell: ANTHROPIC_API_KEY. Not in git
     .env.shared   settings shared by every host; your .env wins
     README.md     what everything here does

The repo has four zones, and knowing which is which is most of what there is
to learn about OSPREY's layout:

- **Source** — ``profile.yml`` and ``data/``: yours to edit, kept in git.
- **Secrets** — ``.env``: your API keys. Not in git; rebuilds never touch it.
- **Output** — ``build/``: generated by ``osprey build``. Never edit it;
  deleting it is safe.
- **State** — ``var/``: the agent's memory and audit log. Not in git.

Step 2: Read profile.yml — It Is the Curriculum
------------------------------------------------

Open ``profile.yml``. This one file is the manifest for the whole deployment,
and the preset deliberately leaves most of it unset — because every key it
leaves unset is emitted into your copy as a **commented block** you can turn on
later. The hello-world preset's minimalism yields exactly **13** such blocks,
covering everything from a channel database to event dispatch to a virtual
accelerator. Growing this project into a production deployment is, quite
literally, uncommenting one block at a time and rebuilding.

The parts that *are* set are short. The agent's capabilities are lists of
named artifacts from the OSPREY library — eleven hooks (three of which form the
write-safety chain), three rules, and one output style:

.. code-block:: yaml

   hooks:
     - hook-log       # Append every tool call to a structured JSONL audit log
     ...
     # The next three are the write-safety chain, and no write reaches the control
     # system until all three agree. Removing any one of them removes a guard.
     - writes-check   # Kill switch: refuse every write while writes_enabled is false
     - approval       # Gate hardware-write tool calls on human approval prompt
     - limits         # Enforce per-channel min/max limits, from data/channel_limits.json

And all remaining configuration lives in the ``config:`` block, one dotted key
per line:

.. code-block:: yaml

   config:
     # Which control system to talk to. "mock" invents channels in-process, so
     # reads work with no hardware and no containers behind them.
     control_system.type: mock
     # Writes are refused until this is on. Uncomment it, rebuild, and the limits
     # and approval hooks above take over from there.
     # control_system.writes_enabled: true
     # ...

That commented ``control_system.writes_enabled`` line is the one this tutorial
comes back to in Step 7. For everything the profile can hold, see
:doc:`../how-to/build-profiles`.

.. warning::

   ``profile.yml`` is the **only durable edit surface**. The ``build/config.yml``
   you are about to generate is output — every ``osprey build`` wipes and
   re-renders it, so an edit made there is lost on the next build (and a
   session-start check warns you when the build has gone stale). Make changes
   in ``profile.yml`` and rebuild.

Step 3: Build It
-----------------

.. code-block:: bash

   osprey build

``osprey build`` takes no arguments: it walks up from wherever you run it to
the nearest ``profile.yml`` and renders that repo's ``build/`` directory —
``config.yml``, the agent's ``.claude/`` tree (rules, hooks, settings), the
``.mcp.json`` that wires up the MCP servers the agent can call (the
``controls`` server among them), and a copy of your ``data/`` files. The render is complete and disposable: nothing durable lives
in ``build/``.

.. note::

   The first build may take 1--2 minutes to create a virtual environment and
   install dependencies. Subsequent builds are near-instant.

Step 4: Launch the Web Terminal
--------------------------------

.. code-block:: bash

   osprey web

This starts the OSPREY Web Terminal on http://127.0.0.1:8087 — a browser
interface with the agent in a terminal pane on the left and a live workspace
viewer on the right, where plots and other artifacts the agent produces appear.
The command prints a login URL (``http://127.0.0.1:8087/?token=…``) once, at
startup; opening it sets a session cookie and redirects to the clean address.
The token is the server's own secret, so treat that URL like a password.
No containers are involved; it is a local process serving your ``build/``.
It refuses to start if there is no build yet, so run ``osprey build`` first.

Useful variations: ``osprey web --port 9000`` picks another port,
``osprey web --repo ~/my-first-agent`` serves the deployment from anywhere, and
``osprey web stop`` stops a backgrounded (``--detach``) instance. See
:doc:`../how-to/web-terminal/index` for the full tour.

.. note::

   Prefer to stay in your terminal? ``osprey chat`` starts the same agent
   against the same build as a plain CLI session — see
   :doc:`/how-to/agent-interfaces/cli-agent`. Everything below works identically there;
   this tutorial assumes the web terminal.

Step 5: Read Some Channels
---------------------------

The mock connector accepts **any** channel name and invents a plausible value
for it — that is the whole trick behind a five-minute first session. Try:

.. code-block:: text

   You: Read channel SR:BEAM:CURRENT

The OSPREY agent calls the ``channel_read`` tool on the ``controls`` MCP server
and reports back a value with units and a status. The exact wording varies with
the agent's output style, but it looks roughly like:

.. code-block:: text

   SR:BEAM:CURRENT  250.3 mA  OK

Reads need no approval — only writes are gated. Ask for several at once:

.. code-block:: text

   You: Read SR:BEAM:CURRENT and SR:MAG:QF:01:CURRENT:RB

Historical questions work too — "plot the beam current over the last hour" —
because a mock archiver backs the ``archiver_read`` tool with synthetic
history, and the plot lands in the workspace pane beside the terminal.

Step 6: Attempt a Write — and Get Refused
------------------------------------------

Now ask for a write:

.. code-block:: text

   You: Set SR:MAG:QF:01:CURRENT:SP to 150

The write is refused before it reaches the control system: the agent reports
that writes are disabled in this deployment. The exact wording is the agent's
own, because the refusal happens a layer below it — with the switch off,
``osprey build`` renders the write tool into the agent's denied permissions,
so the tool call is blocked before it even executes.

This is the first of **three guards** that every write must pass:

1. **Master switch** (``writes-check`` hook) — ``control_system.writes_enabled``
   is ``false`` by default, so all writes are refused outright. This is what
   just fired: the build bakes the switch into the agent's denied permissions,
   and the ``writes-check`` hook enforces the same switch again as defense in
   depth.
2. **Limits** (``limits`` hook) — the value is checked against per-channel
   bounds and writable flags in ``data/channel_limits.json``.
3. **Approval** (``approval`` hook) — a write that passes both still pauses
   for your explicit yes/no before anything is executed.

Safety is not optional equipment here: the three hooks are declared in your
``profile.yml``, and removing any one of them removes a guard.

Step 7: Enable Writes — in profile.yml
---------------------------------------

Open ``profile.yml``, find the ``config:`` block from Step 2, and uncomment
one line:

.. code-block:: yaml

   config:
     control_system.type: mock
     control_system.writes_enabled: true   # ← was commented out

Then re-render and relaunch:

.. code-block:: bash

   osprey build
   osprey web

Do **not** edit ``build/config.yml`` to flip this switch — that file is
generated output, and your edit would vanish on the next build. The profile is
where the change belongs, and the rebuild carries it into the render.

Step 8: Write with the Guards Watching
---------------------------------------

The limits database that ships with this preset, ``data/channel_limits.json``,
declares three channels: two writable quadrupole setpoints with bounds, and one
read-only measurement. With writes enabled, all three remaining behaviors are
now observable.

**A write inside its limits** — pauses for your approval:

.. code-block:: text

   You: Set SR:MAG:QF:01:CURRENT:SP to 150

150 sits inside the 0--300 range declared for this channel, so the limits
check passes and the approval prompt appears in the terminal, naming the
channel and value. Approve it, and the mock connector accepts the write.
Nothing is ever written without this step.

**A write outside its limits** — blocked:

.. code-block:: text

   You: Set SR:MAG:QF:01:CURRENT:SP to 500

500 is above the channel's maximum of 300, so the write is refused: the
``limits`` hook denies it, and the connector checks the same limits database
once more at execution time — so even an approved write cannot carry an
out-of-range value to the (mock) hardware. Approval is a gate on writes the
limits allow; it is not a way around them.

**A write to a read-only channel** — blocked regardless of value:

.. code-block:: text

   You: Set SR:BEAM:CURRENT to 1.0

``SR:BEAM:CURRENT`` is a measurement, marked ``"writable": false`` in the
limits database, so the write is refused whatever the value.

Step 9: Edit the Limits Database
---------------------------------

``data/channel_limits.json`` is your first editable safety artifact. The
shipped file looks like this (comments abridged):

.. code-block:: json

   {
     "defaults": {
       "writable": true,
       "verification": {"level": "callback"}
     },
     "SR:MAG:QF:01:CURRENT:SP": {"min_value": 0.0, "max_value": 300.0},
     "SR:MAG:QD:01:CURRENT:SP": {"min_value": 0.0, "max_value": 250.0},
     "SR:BEAM:CURRENT": {"writable": false}
   }

Channels not listed here are still writable — the preset sets
``allow_unlisted_channels: true`` so the mock's invented channels stay usable;
a production deployment sets it ``false`` so an unknown channel fails closed.
Listing a channel is how you put bounds on it. Add one:

.. code-block:: json

   "SR:MAG:CORR:01:CURRENT:SP": {"min_value": -5.0, "max_value": 5.0}

Then ``osprey build`` to carry the change into the render, and try writes on
either side of the new bounds. This edit-rebuild-observe loop — in ``data/``
or in ``profile.yml`` — is the same loop every real deployment is grown with.

Step 10: First Containers — Deploy the Telemetry Store
-------------------------------------------------------

Everything so far ran container-free. The preset declares exactly one
containerized service, and this is the deployment lesson:

.. code-block:: bash

   osprey up -d

This needs a container runtime (Docker or Podman) and starts **OpenObserve**, a
local telemetry store bound to localhost, with its UI at
http://localhost:5080. The agent already emits its logs and metrics there, so
``osprey up`` plus ``osprey web`` gives you a queryable record of every
session out of the box — see :doc:`/how-to/health-and-monitoring/monitor-agent`. Stop the stack
with ``osprey down``; the agent itself keeps working without it.

The commands you now know are the complete lifecycle, and they are the same
for a production facility deployment: ``osprey init`` once, then edit →
``osprey build`` → ``osprey up`` / ``osprey web`` forever after.
